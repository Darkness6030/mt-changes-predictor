# Инструкции агентам проекта

## Контекст и источники

Проект: ранний прогноз задержек наземного транспорта на хакатоне Московского транспорта.
Рабочий язык общения и документации — русский; имена Python/API — английские.
Начать с [README](README.md) и раздела «Точка продолжения» в
[docs/PROGRESS.md](docs/PROGRESS.md): там фактическое состояние и конкретные следующие задачи.
Затем прочитать [RULES](docs/RULES.md), [PLAN](docs/PLAN.md) и [README датасета](dataset/README.md).
[RESEARCH](docs/RESEARCH.md) и `docs/research-*.md` — обоснование решений, не статус реализации.
При работе с потоком обязательна `dataset/docs/Emulator-and-Telematic-Packets-Specification.md`.
Первичные требования: `docs/description.md`, `docs/messages.md`, PDF задания в `docs/`.

При противоречии различать регламент и состояние: требования подтверждать первичными
источниками, реализованное — кодом/тестами и свежей записью PROGRESS; исторический research
не доказывает, что функция сейчас отсутствует или уже готова. Не считать этап PLAN выполненным
без кода и проверки. Рабочий файл называется **`AGENTS.md`** (верхний регистр).

## Старт после клонирования

Все команды из корня, Python 3.12; `.venv` и `artifacts/` после clone отсутствуют.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r ml/requirements.lock
.venv/bin/python -m pip install --no-deps -e ml
.venv/bin/python -m pytest -q
.venv/bin/python -m transport_ml predict --model ml/pretrained/v1 --output artifacts/onboarding/submission.csv
```

Последняя команда создаёт новый файл; при повторе выбрать новый output. Эталонный готовый
CSV — `ml/pretrained/v1/submission.csv`. Обучать заново для знакомства не требуется.
Рабочий вход — `python -m transport_ml`; `main.py` пуст и не используется.
Подробности Docker и воспроизведения — [ml/README.md](ml/README.md).

- До параллельной реализации Backend/UI записать версию API-контракта и пример snapshot

- FeatureBuilder/scheme меняет ML-направление; Backend импортирует библиотеку. При изменении

- Коммитить свою задачу; не делать force push, не сливать и не перетирать работу напарника
  автоматически. После задачи записать результат, команды, метрики, ограничения и следующий шаг.

## Приоритеты

1. Честный ML-прогноз signed задержки в секундах за 10–15 минут, воспроизводимая оценка.
2. Единые признаки в offline/replay/live и работающий приём NDTP.
3. Разделение Backend/ML, понятный диспетчерский UI, устойчивость и Docker-запуск.
4. Документация, валидный CSV и подготовка обеих частей сдачи до 27 сентября 23:59 МСК.

Следовать P0/P1/P2 в PLAN; не внедрять дополнительные сервисы, GPU/LLM или новый UI-стек
без пользы для текущего этапа. При неоднозначности принимать обратимые локальные решения
и фиксировать допущения. Не отправлять сообщения организаторам и не загружать решения
на платформу без инструкции пользователя. Работать одним агентом, если пользователь
отдельно не запросил делегирование.

## Инварианты данных и ML

- Для `(tr_id, T)` использовать только `event_time <= T`; будущее плановое расписание допустимо.
- Цель — первая плановая остановка в `(T+600 с, T+900 с]`; известные target keys сохранять.
- Delay = факт минус план. Не запрещать отрицательные predictions.
- `cur_dev_s` разрешён в offline-точках. В live получать причинно из состояния/наблюдений;
  если не получается, отмечать пропуск и использовать проверенный fallback.
- `time_fact_begin`, `target_delay_s`, `target_class` не входят в inference-features.
  Факты расписания не читать через вспомогательные feature joins.
- Test/validate traffic совпадают; test schedule содержит факты для того же плана, что
  validate. Не восстанавливать скрытые ответы из этого пересечения или будущей телеметрии.
- Не обучаться на validate-ответах и не использовать идентификаторы как lookup ответов.
  Fit преобразований только на train fold; synthetic families не разделять между folds.
- Raw CSV не изменять. Пропуски, невалидный GPS, дубли, stale и выбросы обрабатывать явно.
- CSV timezone не задан; не назначать UTC/МСК без проверки. Сохранять временную точность.
- `unit_id != tr_id`; применять явный mapping. `target_stop_id` — ID планового посещения,
  не постоянный ID физической остановки. Колонок route/trip/doors в CSV нет.

## Организация реализации

Структура: `ml/`, `backend/`, `frontend/`. Python 3.12+, CatBoost как первая модель,
FastAPI как Backend; точные версии зафиксировать при реализации зависимостей.
Обучение, feature builder, inference, NDTP и API разделять по ответственности.
Финальная Docker-поставка — три модуля ML service / Backend / UI, не монолит (критерий PDF).
Повторно использовать одну функцию признаков, не создавать независимые batch/live версии.
Не обучать модель в HTTP-запросе; API хранит версию модели и время/качество данных.
В состоянии ТС и TCP-буферах ограничивать память, в UI показывать устаревание.
Не обещать вероятность без калибровки и подтверждённую причину без источника.

NDTP: TCP — поток байтов; не приравнивать `recv` к кадру. Проверять размер, CRC и границы;
не пропускать неизвестные ячейки по выдуманной длине. Использовать исходную спецификацию.

## Проверка изменений

Для соответствующих изменений обязательны содержательные проверки:

- cutoff: изменение событий после T не меняет признаки/предикт;
- отсутствие фактов расписания в inference;
- границы горизонта +600/+900 и выбор целевого посещения;
- равенство batch и streaming на одном префиксе событий;
- NDTP: правильный кадр, дробление/склейка TCP, CRC, reconnect и invalid GPS;
- обработка пустой истории, незнакомого unit и устаревших данных;
- submission: UTF-8, `;`, ровно `sample_id;prediction`, все 151 ID текущего validate,
  без дублей, NaN/inf и лишних колонок;
- сквозной smoke test и Docker build после интеграционных изменений.

Не писать тесты, которые только повторяют реализацию, и не запускать обучение ради
редакционных правок. Пока инструменты не созданы, не указывать вымышленные команды как
рабочие. По мере реализации добавить точные команды setup/train/evaluate/replay/serve/test
в README и поддерживать их актуальными. Метрики сопровождать split/seed/config/commit.

## Git, артефакты и прогресс

Не коммитить `.env`, токены, `.venv`, IDE, кэши, Docker-слои и большие модели.
Исключение для передачи команде: небольшой зафиксированный `ml/pretrained/v1/` уже хранит
модели и CSV первого запуска. Не менять v1 на месте; эксперименты писать в `artifacts/<run>/`.
Исходные CSV включены в приватный репозиторий для воспроизводимости; OCI-образ остаётся
локальным. Не менять публичность репозитория и не удалять исходные файлы по собственной
инициативе. Не делать force push и не переписывать чужую историю без указания пользователя.

Журнал находится в `docs/PROGRESS.md` (пользователь перенёс его из корня). При задачах
добавлять только фактические итоги: дата, изменение, проверка/метрика, ограничения,
следующий шаг. PLAN — будущая работа, PROGRESS — выполненная; не смешивать их.
В итоговом ответе кратко указывать изменения, реально выполненные проверки и блокеры.

Единый стиль: Ruff (100 символов, import sorting), dataclass-конфигурации, комментарии
для сложных инвариантов. Перед завершением ML-правок: `.venv/bin/ruff check ml`,
`.venv/bin/ruff format --check ml`, `.venv/bin/python -m pytest -q`.
