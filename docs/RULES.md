## 1. Сдача и оценка — из материалов организаторов

- Обязательны **две** части: CSV в разделе Data Science и форма «Загрузка решения».
- Обе доступны до **27 сентября, 23:59 МСК**. Для CSV засчитывается лучший результат
  за всё время, для формы — последняя сохранённая версия.
- На команду в день: максимум **36 общих попыток**, включая ошибочные, и **24 успешные**
  со score ≥ 0. Момент ежедневного сброса квот в материалах не указан.
- Метрика — MAE прогноза задержки в секундах, ниже лучше.
- Формула: `score = max(0, min(1, (mae_zero − MAE) / (mae_zero − MAE_TARGET)))`.
  `mae_zero = mean(abs(target))`; MAE_TARGET в раздаче не указан.
- README сообщает ≈0,40 для baseline `prediction=cur_dev_s`; это не гарантированный
  score новой отправки. Нулевой прогноз соответствует score 0 по описанию.
- Организаторы требуют ML-решение, работающее в потоке, и проверяют им полученный score.
  Нечестное получение лучшего score аннулирует его: за критерий №1 выставляется 0.
- В Q&A сказано, что баллы целые. Полная таблица ниже взята из PDF (страницы 3–6);
  не обещать дополнительные баллы за функцию вне этой таблицы как гарантию.

## 2. Точный контракт задачи

Для точки `(tr_id, T)` предсказать signed задержку на **первом плановом посещении**
в окне `(T+10 минут, T+15 минут]`. Левая граница исключена, правая включена.
В размеченных точках целевое посещение уже задано `target_stop_id` и `target_time_begin`.

- `target_delay_s = time_fact_begin − time_begin`, секунды.
- Положительное число — опоздание; отрицательное — опережение. Не обрезать ответ снизу нулём.
- `target_stop_id` соответствует `tt_action_item_id`, то есть ID планового прибытия.
  Соединять с расписанием по `(tr_id, target_stop_id)`, проверять время и уникальность.
- `cur_dev_s` — разрешённая подсказка: задержка на последней уже пройденной остановке,
  известная на T. Это не будущий target и не гарантия, что подсказка придёт в NDTP.
- `target_class` справочный: early/ontime/late, пороги −60 и +120 секунд. Граничное
  равенство проверить по разметке перед реализацией классификатора; поле запрещено
  как вход inference, потому что получено из target.
- Платформа принимает величину задержки, а не вероятность класса.

## 3. Честность и предотвращение утечек

Официальное правило: только данные, доступные на T, в том числе телеметрия
`event_time <= T` и `cur_dev_s`. Правила реализации ниже обеспечивают это ограничение.

1. Никаких событий после T, будущих окон, backward fill из будущего и интерполяции
   между прошлой и будущей GPS-точкой. Агрегаты соседних ТС также обрезать по T.
2. Плановое будущее расписание допустимо. Будущее **фактическое** время, target и
   target_class допустимы только как разметка для обучения/оценки.
3. Слой признаков использует явный allowlist; в MVP полностью исключить `time_fact_begin`
   из feature pipeline. Исторические факты разрешать только после доказательства,
   что они были доступны на T, и отдельной проверки равенства batch/online.
4. Test/validate traffic совпадают; validate plan равен test schedule без факта.
   Нельзя использовать это пересечение для извлечения скрытых ответов, подстановки
   фактических задержек или реконструкции генератора датасета.
5. Сырые ID прогнозной точки, пакета и целевого посещения — ключи, не признаки для
   запоминания ответа. Обычный train/test split по строкам не доказывает обобщение.
6. Fit preprocessing, imputation, target encoding и подбор параметров выполнять только
   на обучающей части локального split. Не включать held-out labels в такие вычисления.
7. Синтетические копии одной траектории не распределять между train и holdout;
   если семейства неизвестны, явно ограничить выводы и оценить реальные данные отдельно.
8. В реальном потоке использовать только уже полученные события. `receive_time`
   содержит аномалии; официальную event-time оценку и реалистичную оценку доставки
   описывать раздельно. Не объявлять их эквивалентными без проверки.
9. Обогащение данных допустимо по Q&A при улучшении метрики и корректном использовании.
   Фиксировать источник, доступность на T и отсутствие скрытого target.
10. Не выдавать формулу-baseline за обученную модель, локальный MAE за платформенный score,
    offline-прогноз по полному дню за онлайн-инференс или несуществующие тесты за пройденные.

## 4. Форматы, данные и очистка

- CSV раздачи: UTF-8, разделитель `,`. Submission: UTF-8, разделитель `;`.
- Разметка train/test в `dataset/labels/`; validate labels отсутствуют.
- Реальный шаблон — `dataset/sample_submission.csv`; упоминание
  `submission_template.csv` в начале README не соответствует имени локального файла.
- Submission: ровно `sample_id;prediction`, ровно 151 строка данных в текущей раздаче,
  все ID из `validate/points.csv`, без дублей, NaN, infinity и лишнего index-столбца.
  Сохранять порядок шаблона для повторяемости, хотя основная связь — по ID.
- `prediction` — конечное число в секундах, с сохранением знака. Проверять результат
  повторным чтением готового файла, а не только dataframe до записи.
- Времена CSV без timezone, train содержит дробные секунды до наносекунд. Не округлять
  T до минуты при join и не допускать случайного попадания события после T из-за округления.
- Часть ТС не имеет labels; это контекст, а не потерянные targets. Train содержит синтетику,
  test/validate по README реальные; это не означает независимость их временных периодов.
- Есть invalid GPS, пропуски, нулевые координаты, скорость 368 км/ч, длинные разрывы,
  повторные vehicle-time и `receive_time < event_time`. Очистка должна быть детерминированной,
  одинаковой offline/online и сохранять признаки качества/возраста данных.
- Не считать повторы времени автоматически одинаковыми пакетами. Определить tie-break
  и правила дедупликации; не выбрасывать разные события без проверки.
- Геометрия WKT `POINT (lon lat)`: порядок долгота, широта. `geom` не готовый маршрутный граф.
- В CSV нет дверей, trip/route ID и полилиний. Не имитировать отсутствующие источники
  как реальные; восстановленные маршруты и причины явно обозначать как оценку.

## 5. Продукт и архитектура

**Ключевые требования ТЗ:**

- Прогноз строго в горизонте 10–15 минут до события.
- Независимые по ответственности Backend (API/оркестрация) и ML (обучение/инференс).
- Непрерывный приём NDTP, сопоставление с планом, очистка и производные признаки.
- Прогноз задержки и риска, оценка ошибки, выявление предшествующих паттернов.
- Понятный диспетчеру интерфейс: сеть/карта, положения ТС, зелёный/жёлтый/красный риск,
  карточка инцидента с ТС, прогнозом, предполагаемой причиной и участком.
- Низкая задержка, устойчивость к обрыву связи и деградация без падения; возможность
  дообучения и масштабирования. При последнем известном состоянии показывать stale.

В разделе «Общие требования» сказано, что он рекомендательный, но внутри Docker назван
обязательным. Рабочее решение команды — **обязательно подготовить Docker**, чтобы выполнить
более строгую трактовку. Дополнительно PDF включает Docker непосредственно в критерий №3
и обязательные артефакты, поэтому считать его частью необходимой поставки.
Python 3.12+, PyTorch/CatBoost — рекомендуемый стек; обязательного
совместного использования двух ML-библиотек не установлено. OpenAPI и PyDoc/Sphinx включить
в поставку. GPU поощряется, но не подменяет качество и причинную корректность.

**Детализация оценки из PDF:**

- Горизонт проверяют на потоке, а не только в CSV; алерт после события не считается ранним.
- Три модуля, не монолит; Swagger отвечает на пробный запрос; NDTP→прогноз→UI работает.
- Картина проблем понятна примерно за 5 секунд без инструкции; UI обновляется по потоку.
- Ориентир latency инференса <1–2 с на поток ТС; честные измерения принимаются и без
  полного нагрузочного теста. Нужны throughput без растущих очередей, восстановление
  после reconnect и предсказуемый холодный старт Docker. Отсутствие измерений снижает
  балл, но при корректной архитектуре, по PDF, не обязательно обнуляет его.

**Уточнения Q&A (заметки, не формальная спецификация):**

- Приоритет — предсказать задержку; рекомендации действий очень желательны, но дополнительны.
- Основной пользователь — диспетчер. Карта масштабируется в пределах Москвы, карточки
  кликабельны; удобный путь пользователя приоритетнее перегруженного интерфейса.
- Собственный сервер приёма нужен команде: эмулятор работает клиентом.
- UI может быть сайтом или мобильным приложением; веб-дашборда достаточно для основы.
- Авторизация, новое ТС, глубокая оптимизация выпуска/смен, мобильный клиент — вне базы.
- ТС упрощённо можно считать автобусом/электробусом. Нормативы смен/обедов обещаны
  неуверенно, в раздаче отсутствуют; не превращать примеры Q&A в обязательные нормативы.
- По ДТП достоверных данных нет. Объяснения — наблюдаемые паттерны и гипотезы.
- Q&A упоминает эталон map matching и примерно ±2,5 минуты, но отдельного графа в текущих
  файлах нет. Это не разрешение расширить прогнозное окно или изменить MAE.
- What-if, сложный map matching, ансамбли, ONNX/TensorRT — дополнительные улучшения.
- LLM-агент не входит в ТЗ; в заметках отдельно оговорены российские разработчики.
  Это условие не распространять автоматически на весь технологический стек.

## 6. NDTP: обязательные детали реализации

Полная бинарная спецификация — в [исходном документе](../dataset/docs/Emulator-and-Telematic-Packets-Specification.md).

- Эмулятор: REST на 18080. `GET /api/cells`, `GET /api/config`, `POST /api/config`.
  POST полностью заменяет конфигурацию и запускает отправку; `units: []` останавливает её.
  После рестарта конфигурация теряется; после POST сбрасывается состояние генератора.
- Сервер команды слушает `targetHost:targetPort`; на каждый unit отдельное TCP-соединение.
  Handshake → пауза 200 мс → realtime → отправки по расписанию; обрыв ведёт к reconnect.
  Ответы сервера эмулятор не разбирает, но полноценность протокола за пределами данного
  эмулятора этим не доказана.
- `unitId` уникален, диапазон 0…2147483647; ровно одно `intervalMs > 0` или Spring cron
  из шести полей. Максимум одна Nav00, неизвестный type конфигурации даёт HTTP 400.
- Бинарные числа little-endian, packed. Кадр: NPL 15 байт + NPH 10 байт + тело.
  NPL signature `0x7E7E`, `dataSize` — размер NPH и тела, не всего кадра; type `0x02`.
- CRC-16/Modbus: poly `0xA001`, init `0xFFFF`, по NPH+телу; в поле NPL байты CRC
  переставлены. Эмулятор указывает flags crc=0, но поле CRC всё равно рассчитывает.
- NPH handshake: service=0/type=100, тело 18 байт, версия 6.2.
  Realtime: service=1/type=101. Счётчик NPH requestId отличается от NPL requestId=0.
- Ячейка: `type:u8`, `number:u8`, затем payload. Общей длины каждой ячейки в заголовке
  нет: нельзя безопасно «пропустить неизвестный type» без таблицы размеров.
- Nav00 идёт первой, payload 26 байт; координаты unsigned / 1e7, знак latitude из bit5
  (1=N), longitude из bit6 (1=E), valid из bit7. Timestamp — Unix seconds, speed — км/ч.
- Документированные payload: IntSensor02=26, Usi08=6, Can10=37, Termo16=8, Lls15=50 байт;
  двухбайтный заголовок ячейки учитывать отдельно. Для остальных типов получать точную
  бинарную схему, не выводить длину только из списка JSON-полей.
- При `autoGenerate=true` и пустом cells генерируются Nav00/Usi08/Termo16/IntSensor02/Can10.
  Nav00 добавляется даже при отсутствии в конфиге; timestamp назначает сам эмулятор.
- `unitId`/peerAddress соответствует `unit_id`, а не автоматически `tr_id`.
  Неизвестное устройство показывать как несопоставленное, не присваивать случайному ТС.
- Автогенерация — случайное движение около Москвы, не эталонное выполнение расписания.
  Проверять транспорт и парсер на эмуляторе, ML-качество — на causal replay с labels.
- В текущей папке есть OCI-layout `dataset/ndtp-telemetry-emulator/`, но нет `.tar` из
  инструкции. Проверить поддерживаемый Docker импорт и архитектуру; не обещать запуск
  командой с отсутствующим файлом. Docker-образ исключён из репозитория.

## 7. Правила работы команды

- Сначала P0: данные → честная модель → поток → интерфейс → воспроизводимость → две сдачи.
- До изменения модели фиксировать baseline и split; после — сравнение с ними и абляции.
- Проверять только существенные контракты: causal cutoff, target selection, NDTP,
  batch/online parity, submission, деградацию и сквозной запуск.
- Сохранять исходную раздачу неизменной; производные данные и модели писать в artifacts.
- Не коммитить секреты, `.env`, виртуальное окружение, кэши, IDE и большие Docker-слои.
- Репозиторий исходно приватный. Доступ жюри и способ передачи исключённых артефактов
  обеспечить к сдаче; создание приватного репозитория само по себе этого не решает.
- У каждой метрики указывать набор, split, commit, модель и способ вычисления.
- Вести факты в `docs/PROGRESS.md`; не объявлять пункты плана выполненными заранее.
- При противоречиях отличать прямое сообщение организаторов, исходное ТЗ, заметки Q&A,
  измерение на файлах и решение команды. Не скрывать неопределённость выдуманной нормой.


## 8. Единый стиль кода и текущая реализация

- Корневые части: `ml/`, `backend/`, `frontend/`; все три модуля имеют рабочие
  Dockerfile и объединены Compose. Backend использует общую библиотеку признаков,
  инференс выполняется отдельным ML HTTP-сервисом.
- Python 3.12, snake_case, небольшие функции/модули по ответственности, dataclass для
  конфигурации, явные названия единиц (`_s`, `_kmh`, `_m`). Строка до 100 символов.
  Автоформатирование и порядок импортов — Ruff, настройки в корневом `pyproject.toml`.
- Публичные границы типизировать; сложные решения комментировать по причине/инварианту
  (cutoff, tied time, label availability), не пересказывать очевидную строку кода.
  Не добавлять абстракции и независимые batch/live реализации без необходимости.
- Сборка признаков — только `transport_ml.features.FeatureBuilder`; labels загружаются
  отдельно. При одинаковом минимальном plan time у нескольких посещений сохранять ID
  целевой точки из раздачи. Автовыбор без заданной точки детерминирован по ID.
- Выявлены ties: при сортировке по времени и ID альтернативный earliest ID встречается
  у 102 train, 4 test и 4 validate точек; у всех время совпадает, это не более поздняя цель.
- Текущая очистка/пороги фиксируются в FeatureConfig и manifest. NaN — отсутствие данных,
  не нулевая скорость. V3 добавляет признаки расписания, GPS-matching и взвешенного
  по времени движения; v1/v2 сохраняют прежние 44 признака.
- Default v3: 73 признака (schema 2), ансамбли main/fallback, train-only подбор
  по group/forward folds; test — после заморозки рецепта. Протокол и ограничения —
  `ml/reports/ml-v3.md`. V1/v2 сохранены как совместимые исторические модели.
  Классификаторы и Platt сохранены из v2; независимая групповая калибровка не выполнена.
  Семейства/веса синтетики остаются открытым исследованием.
- Отдельно обучен no-hint fallback; при отсутствующем `cur_dev_s` он выбирается автоматически.
  V3 не подставляет GPS-hint в `cur_dev_s`: GPS-оценки входят отдельными признаками.
  V1/v2 сохраняют прежнюю estimated-политику. Не переносить supplied MAE на автономный
  live; event-time evaluator без points не доказывает качество доставки/публикации.
- Артефакт: native CatBoost + manifest с features/order/config/versions/hashes; при
  несовпадении схемы или checksum завершать inference с ошибкой, не угадывать колонки.
- Команды обучения не перезаписывают существующий каталог; новый эксперимент — новый путь.
  Перед выводом метрик/CSV сохранять воспроизводимую конфигурацию и provenance.
- Проверки ML: `ruff check ml`, `ruff format --check ml`, `python -m pytest -q` из
  настроенного окружения. Все рабочие команды — в `ml/README.md`.
