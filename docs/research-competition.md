приёмка, сдача и питч. Это исследование и предложения, не отчёт о реализованном решении.

## 1. Основание и иерархия источников

Прочитаны исходный шестистраничный PDF задания в `docs/`, [текст задания](description.md),
[сообщение об академической честности и Q&A](messages.md), [README датасета](../dataset/README.md),

- **Официальное уточнение:** лучший score проверяют потоковой ML-моделью; нечестный результат

- **Заметки Q&A:** рекомендации действий желательны, интерфейс ориентирован на диспетчера;

## 2. Как распределены 36 баллов

| Критерий | Максимум | Что продемонстрировать | Что теряет баллы |
|---|---:|---|---|
| ML-точность | 6 | Score ≥0,70 и именно обученная потоковая модель, воспроизводящая результат | Утечка, нет валидного CSV, математическая подстановка вместо ML |
| Горизонт | 4 | Прогноз до события, целевое посещение в окне, временная шкала на потоке | Прогноз после события, только статический CSV, разные clocks |
| 3 модуля + Docker | 6 | ML/Backend/BI, NDTP ingest, план, производные признаки, Swagger, сквозной запуск | Несвязанные notebook/UI, сломанный запуск, заглушки модели |
| BI | 6 | Понимание проблемы примерно за 5 с, карта, положения/риски, карточка, live | Статичная картинка, непонятный цвет, stale показан как «норма» |
| Производительность/надёжность | 4 | Latency, отсутствие роста очередей, reconnect, cold start | Только слова, падение при обрыве, скрытое накопление lag |
| Выступление/демо | 3 | Чёткая история с работающим сценарием | Список технологий вместо пользы, неподготовленное демо |
| Глубина темы | 3 | Различие плана/факта, качество GPS, горизонта и модели | Обещания ДТП/экономии/маршрутов, которых данные не подтверждают |
| Ответы жюри | 4 | Обоснование решений, ограничений и воспроизводимости | Противоречие метрик/демо, неспособность объяснить источник target |

Это максимумы, а не гарантированная оценка по чеклисту. Нет основания присваивать
фиксированный +1 за тёмную тему, GPU, авторизацию или LLM.

Шкала ML: <0,10/невалидный CSV → 0; 0,10–0,24 → 1; 0,25–0,39 → 2;
0,40–0,49 → 3; 0,50–0,59 → 4; 0,60–0,69 → 5; ≥0,70 → 6.
Диапазоны перенесены из PDF; округление в промежутках не пояснено.

**Вывод:** за пределами ML остаётся до 30 баллов. Полностью готовая система и понятная
защита важнее ещё одного неподтверждённого ансамбля при неработающем UI. При этом baseline
≈0,40 из README не гарантирует даже 3 балла: организаторы отдельно требуют обученную модель.

## 3. Набор функций для максимального покрытия критериев

### P0 — необходимая поставка

1. Обученная регрессия signed delay и честное локальное сравнение с baseline.
2. Общий причинный feature builder, артефакт/версия модели, валидация submission.
3. Настоящий NDTP TCP ingest с packet framing, CRC, unit mapping и reconnect.
4. Отдельные ML-service, Backend и UI, запускаемые по одной инструкции Docker Compose.
5. Сопоставление с планом, текущее отклонение/его доступность, скорость, простой.
6. Живое обновление карты Москвы, очередь проблем, карточка и фильтры.
7. На карточке T, целевая остановка/план, предсказанное опоздание и ETA, признак stale,
   наблюдаемый паттерн, предполагаемое действие и происхождение прогноза.
8. Минимальная ML-оценка вероятности опоздания с честной проверкой; регрессия остаётся
   отдельным главным target для CSV. Если вероятность не готова, явно назвать это пробелом
   функционального ТЗ и показывать категорию, а не выдуманный процент.
9. Проверяемый ранний алерт, история его появления и восстановление после обрыва.
10. Повторяемый replay с моделью и часы сценария; отдельный официальный emulator smoke.
11. Измеренные latency/throughput/cold start и документация кода/API.
12. Обе части сдачи, доступ к репозиторию/модели/эмулятору, инструкция жюри.

### P1 — преимущества, усиливающие базовые критерии

| Функция | Польза и доказательство | Ограничение |
|---|---|---|
| История решения | Карточка показывает, когда и на каких данных возник алерт | Не выводить факт из будущего раньше virtual clock |
| Действие + подтверждение просмотра | Полный путь диспетчера, меньше потерянных алертов | Ack = просмотр/принятие к работе, не факт выпуска автобуса |
| Группировка алертов и hysteresis | Не спамить одинаковой проблемой каждые 5 с | Пороги выбрать на validation; не скрывать false positives |
| Честная uncertainty | Поддерживает доверие: данных мало / риск высок / прогноз ненадёжен | Интервал/вероятность требуют отдельной проверки |
| Наблюдаемый паттерн + рекомендация | Снижает время разбора | SHAP/низкая скорость не доказывают физическую причину ДТП |
| Сравнение с baseline внутри отчёта | Объясняет ценность ML | Одинаковые точки, cutoff и split, без выборочного показа |
| Режим сбоя в демо | Видимый stale, восстановление, счётчики | Нельзя заменить отсутствие данных старым «здоровым» статусом |
| Восстановленная последовательность остановок | Лучше геопривязка и объяснение | Не выдавать за официальную маршрутную сеть без графа |

### P2 — только после приёмки P0

What-if с явными допущениями; перенос на новые ТС; расширенная маршрутизация;
нейросетевая последовательная модель и ансамбль; ускорение инференса, если есть измеренный
bottleneck; авторизация и роли; мобильный клиент; LLM-помощник.

Дополнительность функции не означает независимую строку оценки. What-if без модели
действия может создать недоказанное обещание эффекта и ухудшить ответы жюри.

## 4. Что именно считать ранним прогнозом

README задаёт **плановое** окно: `600 < target_plan − T <= 900` секунд.
PDF описывает предупреждение за 10–15 минут до события. При задержке в +5 минут
фактическое прибытие будет дальше: плановый горизонт 12 минут → actual lead time 17 минут.
Это не одно измерение. Для early arrival actual lead time, наоборот, сокращается.

Фиксировать раздельно:

- `planned_horizon_s = target_plan − prediction_as_of` — строгий контракт CSV.
- `actual_arrival_lead_s = actual_arrival − first_alert_as_of` — только после наступления
  факта, для локальной ретроспективной оценки; не inference-feature.
- `delivery_lag_s` — как быстро уже вычисленное предупреждение доставлено оператору.
- `target_event_id`, `model_version`, время данных и время публикации — для аудита.

Не обещать, что обе временные величины всегда попадают в 10–15 минут. Уточнить у
организаторов формулировку live-проверки; до ответа соблюдать точный контракт README и
показывать обе величины. Нельзя назначить target по фактическому будущему времени, чтобы
улучшить демонстрацию lead time.

Для независимой концептуальной опоры: GTFS Realtime различает прогноз времени/задержки,
время обновления и неопределённость. Это полезная аналогия модели данных, но текущий
датасет не является GTFS и реализация GTFS здесь не требуется.
[Официальный GTFS Realtime Reference](https://gtfs.org/documentation/realtime/reference/).

## 5. Метрики продукта без вымышленных бизнес-результатов

Главный отчёт: MAE в секундах, baseline и модель на одинаковом наборе, MAE по разрезам,
число прогнозов/покрытие и ограничения split. Для алертов зафиксировать определение late
и правило объединения повторных прогнозов одного посещения до измерения precision/recall.

Дополнительно измерить:

- precision и recall early warnings, количество уникальных ложных предупреждений;
- долю целевых посещений, для которых прогноз доступен, включая stale/unknown;
- распределение lead time, долю случаев с доступным ранним предупреждением;
- latency p50/p95, sample size, throughput и очереди при заданной нагрузке;
- время пользователя от открытия UI до обнаружения проблемного ТС на сценарии.

Последний показатель можно проверить на нескольких знакомых, которые не видели UI,
но записать размер выборки и назвать это usability smoke test, а не исследованием рынка.
Не исключать молча случаи без прогноза из знаменателя и не считать каждый тик отдельным
успешно предсказанным инцидентом.

Для питча корректна гипотеза «диспетчер раньше замечает риск и получает время на решение».
Утверждения «уменьшаем реальные задержки на X%» или «экономим N рублей» потребуют пилота,
модели воздействия и дополнительных данных. В текущей раздаче этого нет.

## 6. Пакет сдачи и формат

Ниже целевая структура поставки, пока не существующая реализация:

```text
README.md                    # краткий старт + ссылки на все входы для жюри
compose.yaml                 # UI + Backend + ML, профиль replay/emulator
.env.example                 # без секретов, объяснённые переменные
submission.csv               # итоговые 151 предсказание
artifacts/model/             # доставляемый модельный артефакт вне обычного Git
reports/model-card.md         # данные, cutoff, split, MAE, ограничения, версия
reports/benchmark.json       # аппаратная среда, нагрузка, latency, queues, cold start
reports/submission-manifest.json # CSV hash, model hash, commit, source hashes
reports/validation.md        # таблицы сравнения и проверки утечек
reports/demo-evidence/       # выбранные скриншоты/логи/короткое резервное видео
docs/JURY_GUIDE.md            # запуск → поток → прогноз → сбой → метрики
site/api-docs/               # сгенерированная PyDoc/Sphinx документация
```

Точные пути определить при реализации. Большие артефакты — отдельная доступная жюри
загрузка/релиз с checksum и командой получения; не оставлять ссылку на локальный ноутбук.
Не ждать обучения при каждом старте: приложить готовую модель, обучение запускать отдельно.
Образ эмулятора в Git отсутствует; включить документированный способ получения/импорта
с проверкой платформы и прав доступа.

| Обязательный пункт формы (PDF, стр. 5) | Конкретный формат | Приёмка перед сдачей |
|---|---|---|
| CSV validate | UTF-8, `sample_id;prediction`, 151 строка, signed seconds | Validator + платформа приняла файл |
| Рабочая система из 3 модулей в Docker | Доступный repo/release, Compose, готовая модель, README | Запуск на чистой машине по инструкции |
| Инструкция жюри | Одна markdown/HTML-страница со ссылками и командами | Человек без знания проекта повторяет сценарий |
| Документация | Сгенерированная PyDoc/Sphinx + доступный Swagger/OpenAPI | API запрос выполняется; docs открываются |
| Производительность/дополнения | Короткая таблица + машиночитаемые результаты | Указаны hardware, нагрузка, N и измеренная версия |

Хостинг публичного сайта не назван отдельным обязательным условием. Доступный web-demo
полезен, но рабочая локальная Docker-поставка остаётся основой повторения. Не менять
приватность репозитория без указания владельца; настроить доступ жюри или предоставить
согласованный архив. Проверить ссылки из сессии без авторизации владельца.

## 7. Предлагаемый сценарий защиты

Официальная длительность питча в локальных материалах отсутствует. Подготовить ядро
примерно на 4 минуты и расширение на вопросы; это рекомендация, не регламент.

1. **Проблема (20–30 с):** диспетчер видит опоздание слишком поздно; показываем решение
   с конкретным предстоящим посещением и временем для действия.
2. **Путь пользователя (60–90 с):** риск в списке → ТС на карте → план/прогноз/горизонт →
   наблюдаемый паттерн → рекомендация → отметка принятия к работе.
3. **Работа системы (30–45 с):** NDTP приходит, версия модели/свежесть меняются;
   показать выбранный replay и отдельно связь с официальным эмулятором.
4. **Достоверность (40–60 с):** MAE vs baseline, разделение train/test, запрет утечек,
   тот же код признаков и инференса, что формирует CSV.
5. **Надёжность (20–30 с):** обрыв → stale/degraded → reconnect → восстановление.
6. **Завершение (15–20 с):** измеренная скорость, ограничения и следующий проверяемый шаг.

Подготовить резервное видео ровно этого сценария, но не выдавать запись за живой показ.
Не показывать несколько минут установку пакетов. Точный сценарий выбирать по holdout,
а не по скрытым validate answers; пример не заменяет общие метрики.

Слайды: проблема/пользователь; демонстрационный путь; три модуля и поток; честные метрики;
надёжность/ограничения; план пилота. На вопросы держать приложения: схемы признаков,
таблицы абляций, график latency, критерии отключения прогнозов при stale.

## 8. Вопросы, которые нужно уметь закрыть

| Вопрос жюри | Подготовить ответ/доказательство |
|---|---|
| Откуда модель знает `cur_dev_s` в реальном времени? | Источник observed deviation, arrival detector, missing fallback и оценка режима без подсказки |
| Почему ваш test не независим? | Признать пересечения, показать дополнительный holdout и ограничения |
| Это просто `cur_dev_s`? | Сохранённая модель, её признаки, абляция, ML vs baseline |
| Откуда 80%? | Classifier, проверка вероятностей, sample size; иначе процент не показывать |
| Почему алерт действительно ранний? | T, план, время выдачи, фактическое прибытие после события, раздельные lead times |
| Где маршрут и двери? | В CSV нет route/trip/doors, геометрия восстановлена и помечена |
| Что при потере GPS/связи? | Stale, TTL, missing features, очередь, reconnect demo |
| Это прогноз или реальное управление автобусом? | Decision support, рекомендация и ack; команды в парк не отправляются |
| Чем подтверждена производительность? | Raw benchmark и параметры среды, не только анимация UI |
| Сможем ли мы повторить? | README, доступ к данным/модели/эмулятору, Compose, JURY_GUIDE |
