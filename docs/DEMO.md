# Инструкция проверяющему: запуск, поток, алерты, метрики

Требуется Docker с Compose v2. Модель и CSV входят в репозиторий, UI собирается локально.
Для карты нужен интернет и ключ JavaScript API Яндекса: задайте
`VITE_YANDEX_MAPS_API_KEY` в корневом `.env` по `.env.example`, затем пересоберите UI.
Без ключа карта показывает сообщение настройки; очередь и управление временем работают.
Все команды выполняются из корня проекта.

## 1. Запуск системы (1 команда)

```bash
docker compose up -d --build --wait
```

Готовность: команда ждёт, пока три контейнера `ml`, `backend`, `ui` перейдут в `healthy`.
Время первой сборки зависит от окружения. Клонирование описано в [README](../README.md).
Готовый Sphinx и OpenAPI — [DOCUMENTATION](DOCUMENTATION.md).

| Открыть | Что там |
|---|---|
| http://localhost:8080 | Дашборд диспетчера |
| http://localhost:8080/docs | Swagger Backend — пробный запрос к API |
| http://localhost:8011/docs | Swagger ML-сервиса |

Порты хоста меняются в `.env` (пример — `.env.example`). Проверка вручную:

```bash
curl -s localhost:8010/health/ready
curl -s localhost:8011/health/ready
curl -s "localhost:8010/api/v1/snapshot?only_attention=true" | head -c 400
```

## 2. Сценарий A: исторический replay размеченного дня (по умолчанию)

Запускается автоматически: телеметрия `dataset/test/traffic.csv` подаётся по времени
события с 08:00 со скоростью 60×, план берётся без фактических времён.

Что смотреть на дашборде:

1. **Шапка — картина за 5 секунд**: требуют внимания, крайние (первый/последний) рейсы в
   риске, активные предупреждения, ТС с прогнозом, устаревшие данные. Технические метрики —
   в панели «Система».
2. **«Где копится опоздание»** над очередью: отрезки между остановками, где по GPS выросло
   опоздание за прогон. Клик открывает ТС и центрирует карту.
3. **Очередь слева**: по умолчанию «Требуют внимания» — по задержке **или** по вероятности
   опоздания ≥ 50 % (бейдж «по вероятности»). Строка — ТС, знаковая задержка, время цели,
   вероятность опоздания, бейдж «первый/последний рейс», свежесть данных. Крайний рейс в
   риске стоит выше.
4. **Клик по строке** → карточка справа: задержка крупно, плановое и ожидаемое прибытие,
   горизонт (строго больше 600 с, не больше 900 с), момент расчёта `T`, **рейс N из M**, участок подхода,
   вероятность опоздания (калибровка проверена вне фолдов), **«Из чего сложился прогноз»**
   (вклады групп признаков в секундах, сумма = прогноз), наблюдаемые основания,
   **what-if «выпустить резервное ТС»** (резерв через 5–30 мин → рейсы без/с резервом),
   предлагаемое действие, «принято в работу» (отметка распространяется на эпизод ТС) и
   **паспорт предупреждения**: первое предупреждение и за сколько минут до плана, тренд
   прогноза, затем фактическое прибытие по GPS и исход (подтвердилось / в норме / в
   другую сторону).
5. **Карта**: цвет и знак маркера соответствуют риску; выбранное ТС подсвечено, показаны
   схема плановых посещений, цветной участок подхода к цели и пройденный трек.
   Клик по маркеру открывает ту же карточку. Легенда раскрывается кнопкой
   «Обозначения карты»; геометрия схематичная, не дорожный маршрут.
6. **Панель системы** (кнопка внизу справа): версии, задержки p50/p95, счётчики потока,
   скрытые GPS-точки (подмена у Шереметьево), измеренное качество, **раннее предупреждение
   на потоке** (сколько алертов подтвердилось, упреждение до фактического прибытия).
7. **Управление внизу**: время источника, диапазон, пауза, скорость 1×…300×,
   сброс прогона (новый `run_id`), выбор демо-источника. Красная метка плавно
   перетаскивается отдельно, после отпускания выполняется один seek и пауза.
   Вне метки drag сдвигает диапазон, его границы меняют размер. Легенда карты —
   в 10 px от нижнего левого края; переходы, подпись и логотип Яндекса скрыты.

При узком окне до 1000 px карточка располагается под очередью и картой; до 640 px
панели идут вертикально и страница прокручивается. На широком экране очередь и
карточка прокручиваются независимо. Все данные доступны и при свёрнутой легенде.

Проверка честности прогноза прямо в UI: в карточке `T` всегда раньше планового
прибытия на 10–15 минут, а «Этот прогон по разметке» в панели системы показывает
фактический lead time. Он может выходить за 10–15 минут и должен измеряться
отдельно: это не тот же показатель, что плановый горизонт.

## 3. Сценарий B: живой NDTP от нашего replayer

Backend — сервер NDTP; клиенты сами подключаются. Наш replayer кодирует телеметрию
раздачи в настоящие кадры NDTP (по соединению на каждый `unitId`).

```bash
export BACKEND_MODE=ndtp                       # Backend слушает 9201, часы следуют за потоком
docker compose up -d backend
docker compose --profile tools run --rm -d ndtp-replay   # 08:00–10:00, 60×
```

Проверка приёма:

```bash
curl -s localhost:8010/api/v1/status | python3 -m json.tool | sed -n '/"ndtp"/,/}/p'
```

Видны `connections_total`, `handshakes`, `realtime_frames`, `crc_errors: 0`,
`invalid_frames: 0`, список `units`. В UI появляются периодические прогнозы из бинарного потока. По умолчанию
forecast points отключены (`status.points = null`). У default v5 `cur_dev` отсутствует:
GPS/плановые оценки входят отдельными признаками в модель без подсказки. Совпадение с
supplied offline-прогнозом не обещается.
`BACKEND_USE_POINTS=true` включает points только для явной диагностики.

Обрыв и переподключение:

```bash
docker kill $(docker ps -q --filter name=ndtp-replay)     # разрыв
curl -s localhost:8010/api/v1/status | grep -o '"disconnects": [0-9]*'
docker compose --profile tools run --rm -d ndtp-replay    # reconnect: handshakes растут
```

Listener не останавливается, ТС постепенно переходят в «устаревшие данные», алерты не
дублируются после восстановления.

## 3a. Сценарий D: поток проверяющих напрямую (как на итоговой проверке)

По уточнению, записанному автором LIVE-DATE-23 в [PROGRESS](PROGRESS.md), ожидаются
`unitId`, маршруты и расписание из датасета. Дословное сообщение в проекте не сохранено.
Эмулятор ставит в пакеты текущее время, поэтому в режиме NDTP дата расписания по умолчанию
подстраивается под дату первого пакета (`BACKEND_PLAN_SHIFT_S` пусто = `auto`, сдвиг только
на целые сутки, время суток не меняется; поток с датой 06.01.2026 даёт сдвиг 0).

```bash
BACKEND_MODE=ndtp docker compose up -d --build --wait    # ML + Backend + UI, приём NDTP
# Клиент NDTP (эмулятор) подключается к TCP <хост>:9201 (NDTP_HOST_PORT в .env)
curl -s localhost:8010/api/v1/status | python3 -c "import json,sys;s=json.load(sys.stdin);print(s['plan'],s['ndtp']['realtime_frames'])"
```

В `status.plan.shift_s` виден применённый сдвиг, в UI — пометка о сдвиге плана. Прогнозы
появляются, когда у ТС накопится ≥3 событий и в окне (T+10, T+15] есть плановое посещение.
Незнакомый `unitId` получает статус `no_mapping` (новые ТС по Q&A вне кейса): прогноз без
расписания ТС невозможен по постановке. NDTP использует Unix-время; CSV не задаёт timezone. Текущая реализация сопоставляет
его с осью CSV без часового смещения и сдвигает только дату. Интерпретация UTC по
распределению плана — допущение реализации, не явное указание в раздаче.

## 4. Сценарий C: официальный эмулятор организаторов

Образ в Git не входит. Источник — [раздача организаторов](https://disk.yandex.ru/d/CA6tsj4aJJ4Aaw)
из PDF задания: скачать `dataset.zip`, извлечь только `ndtp-telemetry-emulator.tar`
(исходные CSV проекта не заменять). Импорт и запуск:

```bash
docker load -i /путь/к/ndtp-telemetry-emulator.tar
docker compose --profile emulator up -d emulator
```

### Переключение из UI

Обычный `docker compose up -d --build --wait` включает панель «Демо / отладка».
Нажмите кнопку текущего источника внизу рядом с «Система»: CSV replay / Наш NDTP-replayer /
Эмулятор организаторов. Все три переключаются без перезапуска Backend-контейнера.
Официальный вариант станет доступен, когда отвечает контейнер emulator.
«Новый прогон» очищает состояние и начинает выбранный источник сначала.
У нашего TCP-replayer можно выбрать скорость следующего прогона. В обоих NDTP-режимах
шкала времени показывает накопленную историю текущего прогона. Автогенерация
официального эмулятора случайная и это подписано.

### Просмотр прошлого в обоих NDTP-режимах

1. Выберите «Наш NDTP-replayer» или «Эмулятор организаторов». После первого снимка
   появится шкала с растущим диапазоном записей.
2. Нажмите «Ⅱ Просмотр», точку шкалы или введите точную дату и время. Карта,
   очередь, карточка и алерты покажут сохранённый снимок; его время подписано внизу.
   Приём NDTP и ML продолжаются. Разные браузеры могут смотреть разные моменты.
3. «К потоку →» возвращает актуальное состояние. Пауза просмотра не управляет
   эмулятором и не перематывает отправителя.

Журнал хранит **опубликованные состояния**, включая прогнозы, известные на момент записи.
Будущие пакеты/ответы ML не переписывают историю. Выбирается последний снимок не позднее
курсора; движения между снимками не дорисовываются. Точное время записи и отставание
от выбранного момента доступны в подсказке «Снимок». Алерты в истории — только чтение;
системная панель и счётчик принятых пакетов всегда показывают состояние сейчас.

Шкалу можно двигать за границы записей: курсор останется там, карта очистится,
сообщение появится в зарезервированной строке сверху. Если выбран будущий момент,
он загрузится, когда журнал до него дойдёт. Истёкшая запись не подменяется свежей.
По умолчанию сохраняются до **2 часов времени источника**, до **7200 снимков** и
**64 МиБ сжатых записей** (срабатывает первый предел), не чаще раза в секунду
реального времени после цикла Backend. При 60× интервалы снимков в источнике могут
быть около минуты и больше при долгом ML. Это дискретный журнал для отладки,
не полная запись каждого пакета. Параметры `BACKEND_VIEW_HISTORY_*` — в `.env.example`.
История хранится в RAM; новый прогон, смена источника и рестарт Backend её очищают.

Панель сама конфигурирует/останавливает отправителей. Не применять ручные команды
`send-ndtp`/`POST /api/config` параллельно с ней. Отключить панель можно через
`BACKEND_DEMO_ENABLED=false`. Импорт и запуск контейнера остаются операцией окружения:
Backend не получает доступ к Docker socket.

### Альтернативный ручной сценарий

Для старой распакованной OCI-раздачи импорт выглядит так:

```bash
tar -C dataset/ndtp-telemetry-emulator -cf /tmp/ndtp-emulator.tar .
docker image load -i /tmp/ndtp-emulator.tar          # ndtp-telemetry-emulator:1.0 (linux/amd64)
docker compose --profile emulator up -d emulator
curl -s localhost:18080/api/cells | head -c 200
```

Эмулятор ставит собственные timestamp «сейчас», поэтому для получения прогнозов план
выравнивается по дате явным параметром (сдвиг показывается в UI баннером):

```bash
export BACKEND_MODE=ndtp BACKEND_PLAN_SHIFT_S=auto
docker compose up -d backend
curl -s -X POST localhost:18080/api/config -H 'Content-Type: application/json' -d '{
  "targetHost": "backend", "targetPort": 9201,
  "units": [
    {"unitId": 664030, "intervalMs": 3000, "autoGenerate": true, "cells": []},
    {"unitId": 913870, "intervalMs": 3000, "autoGenerate": true, "cells": []},
    {"unitId": 2147483000, "intervalMs": 5000, "autoGenerate": true, "cells": []}
  ]}'
```

Ожидаемо: `handshakes` и `realtime_frames` растут, `crc_errors` и `unknown_cells`
остаются нулевыми (разбираются документированные ячейки Nav00/Usi08/Termo16/
IntSensor02/Can10), незнакомое устройство `2147483000` попадает в `unmapped_units`
и **не** получает чужой `tr_id`.

Честная граница: автогенерация эмулятора двигает ТС случайно около Москвы и не следует
расписанию. Этот сценарий доказывает приём бинарного протокола и живую цепочку
«поток → признаки → ML → UI», но не качество прогноза по маршруту. Размеченный сценарий A показывает диагностику, но для v5 test вошёл в обучение:
независимую оценку качества смотреть в отчётах вне фолдов, а не по MAE этого replay.

Остановка: `docker compose --profile emulator stop emulator`, возврат к replay —
`unset BACKEND_MODE BACKEND_PLAN_SHIFT_S && docker compose up -d backend`.

## 5. Метрики и измерения

```bash
curl -s localhost:8010/api/v1/metrics/quality | python3 -m json.tool   # качество
curl -s localhost:8010/api/v1/metrics | python3 -m json.tool           # задержки/счётчики
```

- `offline` — комплект v5: оценка вне фолдов на test (MAE 67,87 с с подсказкой, 80,12 с без
  неё; baseline `cur_dev_s` 93,36 с), т. к. test вошёл в обучение итоговой модели.
  Score 0,86126 сообщён пользователем после публикации v4; точный загруженный CSV
  не подтверждён. Подробно: [отчёт ML v4/v5](../ml/reports/ml-v5.md).
- `early_warning` — раннее предупреждение **на потоке без разметки**: для каждого алерта
  фактическое прибытие берётся из полученных GPS-точек; `confirmed_share`, упреждение
  `lead_s` и доля предупреждений за ≥10 мин. Работает и на живом NDTP.
- `replay_sidecar` — метрика **этого** прогона по разметке test. Для v5 помечена
  `in_sample_note`: модель обучена в том числе на этой разметке.
- `GET /api/v1/hotspots` — отрезки, где копится опоздание; `GET /api/v1/vehicles/{id}/whatif`
  и `/explanation` — what-if резерва и разложение прогноза.
- `performance` — p50/p95 инференса, обращения к ML, цикла Backend и полного пути
  «событие → опубликованный прогноз». Подробности и условия — [`PERFORMANCE.md`](PERFORMANCE.md).

Автономная event-time оценка без forecast points:
`python -m transport_backend.live_evaluation --model ml/pretrained/v3 --output artifacts/live-eval`
(результаты и границы — [отчёт v3](../ml/reports/ml-v3.md); для v4/v5 test в обучении,
поэтому такая оценка на test была бы in-sample).

## 6. Проверка деградации

| Проверка | Команда | Ожидаемое поведение |
|---|---|---|
| Падение ML | `docker compose stop ml` | Backend остаётся `healthy`, статус прогнозов `ml_unavailable`, в UI баннер, прошлые числа с возрастом; новых выдуманных значений нет |
| Восстановление ML | `docker compose start ml` | Прогнозы возобновляются без перезапуска Backend |
| Потеря API у UI | `docker compose stop backend` | В UI баннер «Связь потеряна», последнее состояние не перекрашивается в зелёное |
| API карты недоступен | Заблокировать api-maps.yandex.ru и перезагрузить страницу | Через 15 с сообщение об ошибке и кнопка повтора; очередь, карточка и прогнозы работают. Без API Яндекса геометрия карты недоступна |
| Пауза replay | Кнопка «Пауза» | Виртуальное время и возрасты данных останавливаются, wall-clock health продолжает считаться |
| Сброс прогона | Кнопка «Сброс прогона» | Новый `run_id`, чистое состояние, инциденты не переносятся |

## 7. CSV для Data Science

Готовый файл — `ml/pretrained/v5/submission.csv` (151 строка, `sample_id;prediction`,
побайтово равен v4).
Воспроизведение без обучения и без Docker:

```bash
.venv/bin/python -m transport_ml predict --model ml/pretrained/v5 \
  --output artifacts/check/submission.csv
shasum -a 256 artifacts/check/submission.csv ml/pretrained/v5/submission.csv
```

В Docker:

```bash
docker compose --profile tools run --rm trainer predict --model /app/model \
  --output artifacts/check/submission.csv
```

Повторное обучение (необязательно, ~5 с на 4 потоках):

```bash
docker compose --profile tools run --rm trainer train --model artifacts/new-run
```
