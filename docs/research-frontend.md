# Исследование frontend и диспетчерского продукта

Дата: 25.09.2026. Статус: исследование и рекомендации к реализации, не описание работающего UI. Изучены `AGENTS.md`, [PLAN](PLAN.md), [RULES](RULES.md), [ТЗ](description.md), [Q&A](messages.md), [README данных](../dataset/README.md) и официальная документация технологий. Числа баллов ниже взяты из RULES, которое ссылается на PDF; отдельная функция не гарантирует отдельный балл.

## 1. Решение и вклад в победу

**Выбрать desktop web: React + Vite + TypeScript + Leaflet, CSS без большого UI-фреймворка, отдельный UI-контейнер со статикой и reverse proxy к Backend.** Основной экран — список требующих внимания ТС, карта Москвы и карточка выбранного прогноза. Продуктовая единица — «какое ТС, где, на сколько опоздает и сколько времени есть у диспетчера», а не график работы модели.

В основной оценке BI даёт до 6/26, горизонт до 4/26, интеграция до 6/26, надёжность до 4/26. UI может сделать доказательства трёх последних критериев видимыми, но не заменяет правильный поток и модель. На питче демонстрация и ответы дают ещё до 10 баллов. Приоритет: один проверенный путь от раннего алерта к объяснимому действию; затем честное поведение при обрыве. Мобильное приложение, авторизация, 3D, чат с LLM и сложные конструкторы дашбордов не нужны для базы. Это согласуется с приоритетом CJM сайта и диспетчера в [Q&A](messages.md).

## 2. Сравнение технологий

| Подход | Проверенные возможности | Вывод для проекта |
|---|---|---|
| React + Vite + TypeScript | Vite собирает статические production-артефакты; `vite preview` предназначен для проверки сборки, не production-сервера. [Vite](https://vite.dev/guide/static-deploy.html) | Выбран: один интерактивный экран, типизированный API, состояние выбранного ТС и карты, отдельная дешёвая поставка статики |
| Next.js | Поддерживает static export и размещение HTML/CSS/JS без Node runtime. [Next.js](https://nextjs.org/docs/app/guides/static-exports) | Технически подходит; SSR/SEO и серверные страницы здесь не дают доказанной пользы. Не добавлять второй серверный фреймворк к FastAPI |
| Streamlit | Fragments позволяют перезапускать часть страницы независимо и по интервалу. [Streamlit](https://docs.streamlit.io/develop/concepts/architecture/fragments) | Хорош для внутренней ML-диагностики; финальный управляемый map/list/card UX потребует интеграций. Не строить два UI до завершения P0 |
| Leaflet | Raster layers, GeoJSON, polyline, SVG/Canvas, ограничения границ, keyboard navigation и attribution уже предусмотрены API. [Leaflet](https://leafletjs.com/reference.html) | Выбран для десятков ТС текущей раздачи. Использовать стабильную ветку 1.9.4, не 2.0 alpha; проверить совместимость при фиксации lockfile |
| MapLibre GL JS | WebGL-отрисовка векторных карт и настраиваемые стили. [MapLibre](https://maplibre.org/maplibre-gl-js/docs/) | Имеет смысл при подготовленной векторной подложке/большом объёме. В текущем MVP дополнительные style/tile/font assets усложняют offline-поставку |

React использовать с обычным Leaflet внутри небольшого компонента-адаптера: создать карту один раз, обновлять маркеры по ID, удалять обработчики при unmount. Это рекомендация по снижению числа зависимостей, не запрет React-Leaflet. Версии React/Vite/TS/Node закрепить lockfile и Dockerfile при реализации; не подбирать «самую новую» ценой несовместимости. Простые SVG-графики истории можно сделать без отдельной chart-библиотеки. Подключение к Backend — `fetch`; глобальный state-manager для одного экрана пока не нужен.

## 3. Содержание первого экрана

Макет для ноутбука 1366×768: верхняя полоса около 64 px; слева очередь шириной около 320 px; в центре карта; справа раскрывающаяся карточка около 350 px. При малой ширине карточка заменяет часть карты, а не перекрывает очередь. Это проектные ориентиры, которые надо проверить на реальном экране защиты.

- **Шапка:** название, режим «Живой NDTP» / «Исторический replay», время источника, состояние связи; четыре компактных числа: ТС с прогнозом, требующие внимания, нет прогноза, устаревшая телеметрия. Нельзя считать missing prediction «зелёным».
- **Очередь:** по умолчанию проблемные ТС, сортировка по важности и ближайшему целевому посещению. Строка: `ТС 131672 · +3 мин 10 с · через 12 мин · адрес/участок`. Отдельный badge качества данных. Поиск по ТС; фильтры «Все / Опоздание / Опережение / Нет данных». Не показывать выдуманный номер маршрута.
- **Карта:** точки ТС, целевая остановка выбранного ТС, легенда и ограничение рабочей области Москвы с достаточным полем для наблюдаемых координат. Выбор строки подсвечивает маркер; выбор маркера открывает ту же карточку. Автоцентрирование только по явному действию, без прыжков на каждом обновлении.
- **Карточка:** signed прогноз крупно; плановое прибытие; ожидаемое прибытие `план + прогноз`; момент расчёта; горизонт; наблюдаемые паттерны; качество/возраст данных; предложение диспетчеру. История последних прогнозов относится к одному target или явно показывает смену target.
- **Второстепенная панель «Система»:** model version, режим/fallback, p50/p95, поток пакетов, ошибка API, ссылка Swagger. Технические детали не занимают центр рабочего экрана.

Проверка «5 секунд»: показать экран трём людям, не знакомым с проектом; через 5 секунд спросить, какое ТС требует внимания, где оно и что ожидается. Успех P0 — все три ответа понятны без объяснения легенды. Это предложенный usability-тест, не проведённый результат.

Цвет дублировать текстом, знаком и формой. Фокус клавиатуры видим; из очереди доступны все карточки без точного попадания по маркеру. Не мигающие красные элементы; сильная анимация не нужна. Требование не кодировать смысл только цветом соответствует [WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

## 4. Риск, вероятность и достоверность — разные поля

Первый интеграционный вариант показывает «Уровень внимания по прогнозу», а не выдуманные проценты; это временный fallback с неполным покрытием ТЗ. Предлагаемый UI-порог: зелёный при `−60 <= delay_s <= 60`, жёлтый при `60 < delay_s <= 120` или `delay_s < −60`, красный при `delay_s > 120`. Это **политика продукта**, не официальная разметка `target_class`; пороги вынести в Backend config и раскрыть в легенде. Опережение подписывать явно, иначе диспетчер примет отрицательное значение за хороший исход. Если ML-исследование задаст проверенные пороги/классы, согласовать их до реализации.

ТЗ прямо требует вероятность. Для полного покрытия включить в P0 полной поставки настоящий late-classifier после основной регрессии: `P(delay > 120 с)` с проверкой качества вероятностей на честном holdout и калибровкой при необходимости. UI показывает процент только при наличии проверенного ML-выхода. Если модель вероятности не готова, честно указать неполное покрытие требования; severity остаётся рабочим fallback, но не заменяет вероятность. Нельзя называть нормированную задержку вероятностью. Интервал прогноза показывать только при оценке coverage; общий MAE набора не является персональным интервалом ошибки.

`fresh / stale / missing` — отдельная ось от уровня внимания. Предложение для начальных smoke-тестов: stale после `max(60 с, 3 × ожидаемый интервал)` без валидной позиции; порог уточнить по данным и конфигурации эмулятора. Backend возвращает возраст последнего события, последней валидной позиции и прогноза отдельно. При потере API отображается последнее полученное состояние с баннером «Связь потеряна»; последняя красная точка не превращается в зелёную. При invalid GPS оставлять последнюю валидную позицию с возрастом, а при её отсутствии — только строку без маркера. Если цель в окне отсутствует, писать «Нет плановой остановки в горизонте», не `0 с`.

## 5. Сценарий alert → vehicle → action

1. Прогноз для будущего планового посещения пересекает порог: строка появляется в очереди, маркер получает цвет и знак. Один alert на `(run_id, tr_id, target_stop_id)`; повторный расчёт обновляет его, не создаёт поток дублей.
2. Клик по строке открывает целевое посещение, прогноз +3:10, план через 12 минут, ожидаемое время и evidence: например, «Средняя скорость за 3 минуты снизилась с X до Y», если такой causal-признак действительно вычислен. Нет данных о ДТП/дверях — нет таких утверждений.
3. Рекомендация: «Проверить ситуацию с водителем; рассмотреть оперативное регулирование по действующим правилам». Для long dwell — «Уточнить причину стоянки». Не предлагать превышение скорости, не обещать наличие резерва или допустимость перевода ТС без входных ограничений.
4. P1 «Принято в работу»: Backend фиксирует acknowledgement и время. Это отметка диспетчера, **не доказательство связи с водителем и не выполненное изменение движения**. Реальное управление не реализуется; кнопки «Отправить резерв» с фиктивным успешным ответом не нужны.
5. Закрытие алерта: корректно связать с наступлением target/снижением прогноза/операторской отметкой. При смене target сохранять предыдущий alert в истории. Для P1 добавить hysteresis или несколько последовательных подтверждений; отдельно измерить, сколько раннего lead time это отнимает.

## 6. Временная шкала и два режима

В карточке показать `T → +10 мин (исключено) → target → +15 мин (включено)`. Число `horizon_s = target_planned_at − cutoff_T` рассчитывает Backend. Для допустимой точки `600 < horizon_s <= 900`. Ожидаемое прибытие может оказаться за правой границей, если модель предсказывает задержку: правило выбора target основано на плане, не на предсказанном времени.

Различать три доказательства: плановый горизонт; lead time до фактического события на размеченном replay; wall-clock latency доставки предикта на UI. Нельзя показывать «предупредили за 12 минут» только потому, что target в плановом окне. Факт для оценки открывается в отдельном evaluation-контуре после его наступления, не поступает в inference API.

В replay есть отдельный `simulation_time`, источник данных и скорость 1×/10×/30×, pause/reset. Пауза виртуального времени не делает GPS stale по настенным часам; сетевой health всё равно считается по wall clock. Переход между live и replay создаёт новый `run_id`, сбрасывает историю UI и не смешивает ТС. Случайный NDTP-эмулятор доказывает приём и обновление UI, но не ML-качество на реальных маршрутах. Не скрывать режим «демонстрационный сценарий» или искусственный mapping дат. CSV timezone пока неизвестен: до установления соответствия показывать «время источника, зона не установлена»; браузер не должен сам трактовать строки как UTC/МСК.

## 7. Маршруты и карта без выдуманных данных

В раздаче нет `route_id`, `trip_id` и готовой дорожной полилинии. `target_stop_id` — посещение, не стабильный ID остановки. Для P0 отобразить последовательность плановых точек выбранного ТС на ограниченном отрезке времени и уже наблюдавшийся GPS-трек до T; легенда — «Схема плановых посещений» и «Пройденный трек». Прямая линия между точками не доказывает фактическую дорогу. Разрывать трек при больших пробелах/невалидности; не рисовать будущий фактический GPS. Сеть нескольких таких последовательностей можно показать как реконструированную схему, но не объявлять официальной сетью маршрутов.

Полноценный road map matching — P2 при найденном лицензированном графе, измеримой пользе и достаточном времени. Подсветить риск на схеме участка до target можно уже P0; подписывать степень реконструкции. Координаты GeoJSON — `[lon, lat]`, Leaflet LatLng — `[lat, lon]`; преобразование делать ровно один раз на границе адаптера и проверить точкой Москвы.

## 8. Подложка, сеть и резерв демонстрации

Для небольшого интерактивного демо допустим стандартный URL OSM `https://tile.openstreetmap.org/{z}/{x}/{y}.png`: видимая атрибуция `© OpenStreetMap contributors`, корректный Referer, обычное HTTP-кэширование. Сервис best-effort без SLA. **Нельзя скачивать город/zoom levels заранее, обходить карту ботом для прогрева или паковать эти тайлы для offline**. Для offline нужен собственный источник или провайдер с явным разрешением. [Официальная OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/).

P0: URL и атрибуция конфигурируемые; фронтенд-бандл, шрифты и иконки локальны, CDN не нужен. При отказе тайлов сохранять работающий список, географические overlay и переключение «Схема без подложки» с предупреждением. Это резерв для демонстрации, а не полноценная offline-карта дорог. Подготовить локальный causal replay и запись короткого сценария; видео подписать резервным материалом, не live. Проверять отсутствие сети после production build и отдельно после потери Backend. Не прятать attribution под правой карточкой.

## 9. Предлагаемый API-контракт для согласования с Backend

Имена endpoints — предложение, не реализованные команды. Окончательные схемы должны иметь один источник в Backend OpenAPI.

| Endpoint | Назначение |
|---|---|
| `GET /api/v1/snapshot` | Согласованный снимок fleet, alerts, connection, clock и model status |
| `GET /api/v1/vehicles/{tr_id}` | Плановые точки, causal track, текущий target, история прогнозов и evidence |
| `GET /api/v1/status` | Health и измеренная производительность; ссылка из панели «Система» |
| `POST /api/v1/replay/control` | Start/pause/reset/speed с новым run при reset; только режим demo |
| `POST /api/v1/alerts/{alert_id}/ack` | P1 acknowledgement, идемпотентное повторение |
| `GET /api/v1/events` | P1 SSE-обновления с revision; reconnect делает resync snapshot |

Snapshot: `schema_version`, `run_id`, `revision`, `mode`, `clock`, `server_sent_at`, `vehicles`, `alerts`, `status`. Vehicle: строковые `tr_id`/`unit_id`; nullable position; `position_event_at`, `last_event_at`, `position_age_s`, `telemetry_age_s`, `quality_flags`; prediction с `prediction_id`, `cutoff_T`, `computed_at`, `target_stop_id`, `target_planned_at`, `horizon_s`, `delay_s`, `prediction_status`, `model_version`, `risk_level`; optional `late_probability`, `interval`, `evidence[]` только при наличии. Отдельные статусы `no_target / insufficient_history / fallback / model / unmapped` полезнее одного null без причины.

Backend рассчитывает длительности и проверяет причинность. Точные timestamp передавать строками без потери исходной точности; UI не делает inference join и не округляет T для выбора target. На wall-clock timestamp после установления timezone использовать явный offset; event-time CSV не наделять offset до проверки.

P0: опрос snapshot раз в 1 с, без перекрывающихся запросов, отмена при unmount, backoff при отказе; список обновляет данные без сброса выделения/скролла. Интервал polling входит в end-to-end latency и должен быть измерен. При невозможности выполнить целевой бюджет переключить доставку на SSE. SSE — однонаправленный поток, браузер поддерживает переподключение; события имеют `id`, а heartbeat поддерживает соединение. Но retention/resync и согласованность состояния реализует Backend, не EventSource автоматически. [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events).

## 10. Бэклог, время и приёмка

Оценки — человеко-часы для разработчика, знакомого со стеком, без ML/Backend и без гарантии срока. Общий frontend P0: примерно 13–20 ч с интеграцией и выводом проверенной вероятности (12–18 ч основа + 1–2 ч probability UI); workstream можно вести параллельно на контрактных фикстурах, явно помеченных в dev-режиме.

| Приоритет | Фича / порядок | Время | Вклад |
|---|---|---:|---|
| P0 / 1 | Согласовать контракт, время, null/status, fixture | 1–2 ч | Интеграция, горизонт |
| P0 / 2 | Layout, список, выбор ТС, карта и легенда | 3–4 ч | BI |
| P0 / 3 | Карточка, signed forecast, target timeline, evidence, вероятность при готовом проверенном classifier | 2–3 ч | BI, горизонт, глубина питча |
| P0 / 4 | Snapshot, обновление, stale/error/fallback, режимы | 2–3 ч | Интеграция, надёжность |
| P0 / 5 | Production Docker UI, offline fallback, smoke/demo | 3–4 ч | Интеграция, надёжность, питч |
| P0 / 6 | Проверка 5 секунд и точечные UX-правки | 1–2 ч | BI |
| P1 | SSE при необходимости latency, ack + история | 2–4 ч | Надёжность, удобство |
| P1 | Интервал прогноза при проверенном coverage в ML | 1–2 ч UI + ML | Доверие |
| P1 | Наблюдаемые рекомендации, hysteresis, обзор ошибок replay | 2–3 ч | Питч, глубина |
| P2 | Road matching, what-if с валидированной моделью эффектов, mobile | Не оценивать до P0 | Только после полной поставки |

Приёмочные сценарии, которые следует выполнить и записать как доказательства:

1. **Проблема за 5 секунд:** участники называют ТС, место и задержку; цветовая легенда не требует объяснения.
2. **Причинный ранний прогноз:** replay выдаёт alert при допустимом planned horizon; UI показывает cutoff и target; изменение будущей телеметрии не меняет историю на T. Автоматическая причинная проверка находится в Backend/ML.
3. **Связь списка и карты:** два клика дают карточку и рекомендацию; обновление не теряет выделение; поиск работает и для ТС без GPS.
4. **Missing/early:** отрицательный прогноз отображается как опережение, no-target не равен нулю, неизвестный unit не присваивается чужому ТС.
5. **Disconnect/reconnect:** оборвать NDTP и отдельно HTTP; появляется различимое состояние; восстановление не плодит алерты и не откатывает revision.
6. **Replay pause/reset:** пауза останавливает виртуальные возраста; разрыв API виден; reset создаёт чистое состояние нового run.
7. **Нет интернета:** UI/API/replay работают локально, tile error даёт схему и список. Проверить, что атрибуция видна при нормальной сети.
8. **Горизонт:** +600 исключено, +900 включено; карточка содержит то же target, что Backend, и не выбирает другой в JS.
9. **Latency:** записать время приёма, inference, публикации и отображения; показать p50/p95 и нагрузку. Не выдавать время одного HTTP-request за весь NDTP→UI путь.
10. **Финальная репетиция:** Docker cold start → Swagger пробный запрос → replay alert → карточка/действие → NDTP live → disconnect/reconnect → метрики. Видеорезерв и инструкция жюри воспроизводят тот же сценарий.
