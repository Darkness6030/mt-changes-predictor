# Исследование ML, данных и честной оценки

Дата: 25.09.2026. Статус: исследовательские рекомендации; модель и pipeline здесь не реализованы. Цель — получить максимальные 6 баллов за ML (`score ≥ 0,70`) и доказать ранний прогноз в работающем потоке. Гарантировать score или победу по доступным данным нельзя.

Источники требований: [README датасета](../dataset/README.md), [RULES](RULES.md), [PLAN](PLAN.md), [ТЗ](description.md), [Q&A](messages.md). Внешние первичные источники проверены 25.09.2026; рекомендации ниже — решения команды, а не дополнительные требования организаторов.

## 1. Главные выводы

1. Начать с CPU CatBoost и признаков текущего отклонения, движения, плановой геометрии и качества данных. На 4 434 размеченных строках важнее честная валидация, чем GPU и глубокая сеть.
2. Главный риск интеграции — `cur_dev_s`: разрешён в CSV, но не передаётся как поле Nav00. Нужны причинная оценка пройденной остановки, флаг происхождения и отдельный проверенный режим без подсказки.
3. Train/test/validate не являются независимыми днями. Test/validate traffic совпадают; факты test schedule запрещено использовать для validate. Высокий локальный MAE-score без аудита split не доказывает качество.
4. Синтетика составляет 74,3% train-точек. Вес, полезность и независимость синтетики необходимо проверять отдельно; механическое увеличение объёма не означает увеличение информации.
5. Вероятность задержки — отдельный калибруемый продуктовый выход. `prediction=120` не означает «риск 80%». Для CSV нужна signed регрессия, для UI — проверенная вероятность или честная категория без процентов.
6. Сначала зафиксировать воспроизводимый ML→replay→API контракт; затем тратить ограниченный бюджет на улучшения. Отсутствие рабочего потока рискует потерять больше баллов, чем небольшая прибавка MAE даст.

## 3. Целевой pipeline

1. **Read-only ingest.** Явные схемы CSV; время с полной точностью; никаких молчаливых преобразований timezone. Подготовить отдельный `schedule_plan` с allowlist колонок без `time_fact_begin` сразу на границе данных.
2. **Нормализация.** Валидация GPS, диапазонов, детерминированный tie-break для одинакового vehicle/time, идентификация точных дублей. Отдельно хранить событие и пригодность его координат. Не превращать invalid GPS в истинное положение.
3. **Состояние.** Одинаковые нормализованные события из CSV replay и NDTP; история по ТС с ограниченным окном; mapping `unit_id → tr_id`; возраст последнего события и последнего валидного GPS различаются.
4. **Выбор цели.** В размеченных точках сохранить заданные ключи и проверить их; в live взять первое посещение с `600 < planned_time − T ≤ 900`. Если цели нет, вернуть `no_target`, а не прогноз на другую остановку.
5. **Одна функция признаков.** `build_features(state, plan, tr_id, T, target, cur_dev_context)` не имеет доступа к labels или fact schedule. Для batch вызывать её на таком же префиксе, как в replay.
6. **Обучение.** Train-only preprocessing, контроль synthetic weights, версии конфигурации/семени/данных. Регрессия по MAE и отдельный минимальный классификатор/калибратор риска: вероятность входит в функциональные требования.
7. **Inference.** Версия feature schema, model ID, target, время прогноза, signed delay, uncertainty, источник `cur_dev`, состояние качества и причина fallback возвращаются вместе.
8. **Артефакты.** Model + schema + training config + split manifest + metrics + submission manifest. Обучение не производится в HTTP-запросе.

## 4. Каталог признаков и доступность

Все окна ниже правозамкнутые на T. Ширины 60/180/300/600 с — стартовая гипотеза; не отдельные требования ТЗ. Минимальный набор P0 должен быть готов раньше гео-контекста P1.

| Группа / приоритет | Конкретные признаки | Доступность на T / live parity | Риск и проверка |
|---|---|---|---|
| Текущее отклонение P0 | `cur_dev_s`, missing, source, age | CSV — разрешённая подсказка; live — только причинная оценка | Нельзя читать факт из расписания; оценить отдельно режим без подсказки |
| План P0 | `target_time−T`, число плановых посещений до цели, интервалы между ними | Будущий план разрешён, одинаковый в offline/live | Join только по разрешённым колонкам; не путать ID посещения и места |
| Скорость P0 | Последняя валидная, медиана/квантили/разброс за окна, разность короткого и длинного окна | Только события ≤T; NDTP даёт speed | Отбрасывание выбросов с флагом; пороги документировать |
| Стоянка P0 | Доля времени низкой скорости, длительность непрерывной стоянки, число эпизодов | По истории полученных событий | Взвешивать по длительности, ограничивать вклад больших gaps; остановка не равна ДТП |
| Качество P0 | GPS age, event age, valid fraction, count, gaps, missing speed, history span | Причинно и доступно в обоих режимах | Нулевое число событий не выдавать за нулевую скорость |
| Геометрия P0 | Haversine до цели, bearing mismatch, последние координаты, движение к/от цели | Последний валидный GPS + план | Расстояние по прямой не дорожное; сравнение heading циклическое |
| Время P0 | Час/минута, sin/cos времени суток | Доступно, но timezone требует решения | Один день не даёт проверить день недели/сезон; не обещать эти закономерности |
| Прогресс по плану P1 | Последнее вероятное посещение, расстояние до следующего, оставшаяся длина ломаной | Causal map-to-plan, не нужен будущий факт | Повторные места/развороты/рейсы; confidence и отказ при неоднозначности |
| Динамика P1 | Дистанция по последовательным GPS, ускорение, число остановок, change in cur deviation | Только префикс; не суммировать GPS-скачки | Устойчивость к gaps, invalid и частоте событий |
| Контекст других ТС P1 | Медиана скорости соседей за 3–5 мин, число наблюдаемых соседей | Только их события ≤T; в live лишь реально видимые ТС | Контекст может исчезнуть в live; train dropout и missing flag |
| Геозона P1 | Грубая сетка/кластер места, разрешённая геометрия остановки | Детерминированный transform; обучаемые кластеры fit на train | Не target encoding по всему набору; проверить обобщение по ТС |
| Статистика участка P2 | Исторические travel/dwell times | Только завершённые к T наблюдения; offline нужен временной cutoff | Высокий риск утечки и мало дней; не включать в P0 |

Не использовать как model features: `sample_id`, `target_stop_id`, `packet_id`, `device_event_id`, `time_fact_begin`, `target_delay_s`, `target_class`. `tr_id/unit_id` оставить ключами MVP; сравнение категориального `tr_id` возможно лишь как отдельная абляция с групповой проверкой и unknown-vehicle тестом, не как lookup ответов.

Для скорости по окну простой средний по строкам зависит от частоты телеметрии. Сравнить медиану и ограниченное time-weighted среднее; длинный разрыв не заполнять сохранённой скоростью на часы. Запрещены centered rolling, backward fill и интерполяция с точкой после T.

## 5. Как решить `cur_dev_s` и согласовать live

Nav00 содержит время, позицию, скорость и курс; готового отклонения от расписания нет. Поэтому обученная на идеальной подсказке модель сама по себе ещё не является online-решением.

**P0:** основной регрессор с подсказкой + обученный/проверенный fallback без неё. Не подставлять 0 при пропуске как будто транспорт идёт по графику. В UI/API показывать `cur_dev_source=provided|estimated|missing` и `prediction_mode=normal|degraded`. Пропускную устойчивость можно обучить маскированием подсказки на train; сравнить с отдельной моделью без неё, поскольку распределение estimated отличается от provided.

**P1:** восстановление посещения по упорядоченному плану: кандидат ближайшего допустимого планового посещения + ограничение последовательности + геозона остановки + признаки замедления/выхода из геозоны. Временем прибытия считать момент, выводимый только из уже пришедшего префикса; если фиксация требует выхода из зоны, отклонение станет доступно позже и должно иметь `available_at`. Для повторных остановок и разворотов нужен отказ при неоднозначности. Радиус, минимальное число подтверждений и ограничения скорости выбрать на train replay, не объявлять нормативами.

Оценка: error/coverage reconstructed cur_dev на размеченных train/test-точках, MAE модели с provided/estimated/missing подсказкой, latency подтверждения остановки. Разрешённую CSV-подсказку использовать как reference для этой диагностики. В online fallback нельзя тайно подмешать табличное cur_dev из ближайшей будущей точки.

Случайное движение NDTP-эмулятора вокруг Москвы не является транспортным рейсом. Оно годится для проверки парсера/доставки/деградации, а качество ML демонстрировать на причинном replay реальных CSV. Если для красивого NDTP-демо используется контролируемый план, обозначить его как тестовый сценарий, не как доказательство MAE на городе.

## 6. Честная валидация

**Сначала заморозить split, затем сравнивать модели.** Сохранить sample IDs, временные интервалы, группировку и причины исключений. Обычный random split создаёт оптимизм из-за связанных точек одной траектории.

Предлагаются три отчёта:

- **Организаторский:** обучение на train, оценка на 353 открытых test-точках, без test facts в features. Это близко к доступному benchmark, но не независимый день; не скрывать пересечения.
- **Строгий реальный temporal:** train-real ранняя часть дня → более поздняя часть, с исключением training labels, исход которых ещё не был известен к границе обучения. Консервативный purge должен учитывать горизонт до 15 мин и доступность факта; голые 15 мин не гарантируют отсутствие задержавшихся исходов. Факт можно использовать как metadata split/label-availability, никогда как feature. Для ещё более строгого теста непересекающихся окон добавить embargo по длине feature history и описать его стоимость по объёму.
- **Group robustness:** holdout целых ТС/семейств на реальных данных. Он отвечает на вопрос новых машин и маршрутов, а не завтрашнего дня. 13 реальных размеченных ТС — мало; показывать размеры групп и нестабильность, не только среднее.

`GroupKFold` обеспечивает непересечение заданных групп, но сам не восстанавливает synthetic families; `TimeSeriesSplit` соблюдает порядок, но row-count gap не является временем и не решает групповой leakage. Для этих нерегулярных multi-vehicle точек строить явные индексы split по timestamp и группам. См. первичную документацию [GroupKFold](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupKFold.html) и [TimeSeriesSplit](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html).

**Синтетика:** анализировать сходство входных последовательностей и плана исключительно для группировки и выявления копий; не восстанавливать формулу скрытых ответов. Если родительские семейства достоверно неизвестны, строгие отчёты проводить на real-only и явно пометить all-train результат как имеющий ограничение. Сравнить веса synthetic `0`, `0.25`, `1`; можно уравновешивать суммарный вес семейства, только если его принадлежность известна. Выбор веса — по реальным holdout, не по train MAE.

Test по README дан для локального подбора. После многих попыток его метрика перестаёт быть независимой; лимитировать число экспериментов и сохранять real temporal/group отчёты. До финального freeze не обучать на test labels. Возможный финальный refit train+test допускается только с явным отчётом, что test больше не holdout, и отдельным зафиксированным независимым отчётом; это не базовая рекомендация из-за пересечений и сложности аудита.

## 7. Модели, эксперименты и условия остановки

CatBoost поддерживает MAE и quantile objectives; это даёт прямой путь к целевой регрессии и интервалам. Начальный выбор CPU — проектное решение по малому объёму и простоте поставки, а не доказательство превосходства над всеми моделями. [CatBoost: regression objectives](https://catboost.ai/docs/en/concepts/loss-functions-regression).

| Порядок | Эксперимент | Решение по результату |
|---|---|---|
| E0 | Ноль, train median, cur_dev; replay-correct features; фиксированный split | Без совпадения baseline и cutoff-тестов не продолжать tuning |
| E1 | Малый CatBoost: cur_dev + horizon + время + качество, MAE objective | Получить воспроизводимую обученную точку отсчёта |
| E2 | Скорость, стоянки, distance-to-target | Оставлять блок только при устойчивом улучшении реального holdout |
| E3 | Direct y против residual `y−cur_dev` с обратным сложением | Residual — гипотеза, не гарантированное улучшение; предусмотреть missing режим |
| E4 | Real-only / synthetic weights 0.25 / 1 | Выбор по real holdout и worst-group, не общему train score |
| E5 | Геометрический прогресс/соседи | Сначала доказать causal parity; отклонить, если выигрыш не покрывает сложность |
| E6 | Небольшой ensemble лучших независимых моделей/seed | Принимать лишь после групповых проверок и замера latency |
| E7 | Улучшенные квантили и late-risk; минимальный classifier делается вместе с E2 | Не менять CSV-оценку на risk; минимальную вероятность включить в функциональный MVP |

Стартовый небольшой поиск: depth 4/6, learning rate 0.03/0.08, iterations с верхним пределом 1 000 и early stopping на development fold. Это предлагаемые значения, не выполненные запуски и не оптимальные параметры. После выбора блоков провести только короткую проверку чувствительности. Seed/config зафиксировать; после ранней остановки финальное число деревьев выбирать по development splits, не по validate.

Условия остановки: два последовательных feature blocks без воспроизводимого улучшения — вернуться к интеграции; любой cutoff/parity дефект — остановить продвижение модели; выигрыш только на синтетике или за счёт одной группы — не объявлять победой; за день до сдачи зафиксировать пригодную модель, новые эксперименты только параллельно и с возможностью отката. Практический порог значимого улучшения выбрать до экспериментов, например 2 с MAE на основном real holdout плюс отсутствие крупной деградации отдельных групп; это внутренний ориентир, не статистическая гарантия.

Отчёт: общий MAE, real MAE, MAE по ТС/часам/early-ontime-late/качеству/cur_dev source; p50/p90 absolute error; число наблюдений каждого среза. Интервалы неопределённости сравнения моделей считать блоками ТС/семейств или времени, а не независимым bootstrap строк. При малом числе групп прямо указывать нестабильность.

## 8. Что означает `score ≥ 0,70`

По формуле организаторов, при положительном знаменателе для 0,70 требуется:

`MAE ≤ 0.30 × mae_zero + 0.70 × MAE_TARGET`.

`MAE_TARGET` неизвестен; скрытый `mae_zero` тоже нельзя заменять test-значением. Следовательно, конкретный обещанный MAE «для шести баллов» сейчас рассчитать нельзя. Baseline score ≈0,40 из README и test MAE нельзя объединять в выведенный точный hidden threshold: это разные оценки. В отчёте разделять локальный MAE и реально полученный платформенный score, хранить версии каждой отправки. Не тратить попытки на случайные микроварианты и подгонку к leaderboard.

## 9. Вероятность, интервалы и объяснения

**P0:** показывать signed delay, ожидаемое время, качество входа, возраст прогноза и наблюдаемые сигналы: «низкая скорость 3 мин», «длительная стоянка», «GPS устарел». Категория по прогнозируемой задержке может быть полезна, но это не вероятность. В спецификации UI различать severity задержки и уверенность модели.

**Функциональный P0:** минимальный отдельный binary classifier `P(y>120)` (например, неглубокий CatBoostClassifier или LogisticRegression на небольшом наборе тех же признаков); при необходимости early-risk как P1. Вероятность требуется ТЗ, поэтому заранее запланировать classifier и проверку, а не обещать максимальные баллы с одной регрессией. Обучать и калибровать на непересекающихся temporal/group данных; на небольшом наборе сначала sigmoid calibration. Проверять Brier, log loss, reliability bins с количеством случаев; не использовать дефолтный случайный CV. Isotonic на малой калибровке может переобучаться. Основание: [scikit-learn: Probability calibration](https://scikit-learn.org/stable/modules/calibration.html). При нестабильной калибровке показывать model probability с явным ограничением качества либо временно вернуть risk category без процентов; второй вариант — осознанная неполнота функционального требования, а не полное соответствие ТЗ.

**Интервалы:** отдельные quantile 0.1/0.5/0.9 или MultiQuantile, с проверкой crossing, coverage и средней ширины на holdout. Интервал 10–90% без проверки покрытия нельзя называть гарантированным 80%-интервалом. Проверять real-only и degraded срезы; если данных мало, сообщать ограничение. Не выводить вероятность `P(y>120)` из трёх квантилей произвольной линейной формулой. [CatBoost: quantile objectives](https://catboost.ai/docs/en/concepts/loss-functions-regression).

SHAP/feature contributions можно добавить как внутреннюю диагностику; они объясняют вклад признака в модель, а не причину транспортного события. Слова «ДТП», «перекрытие», «поломка» допустимы лишь при источнике; иначе «возможная задержка движения» с конкретными наблюдениями. Рекомендации диспетчеру давать как проверяемые действия («проверить связь с ТС»), без выдуманных полномочий автоматического изменения маршрута.

## 10. Проверки и комплект доказательств для защиты

Обязательные содержательные тесты:

- Будущая телеметрия изменена/удалена → признаки и прогноз на T идентичны.
- Fact columns и targets подменены → inference не меняется; schema reject при попытке передать их как features.
- Цели на +600 не включаются, +900 включаются; повторное посещение не путается с физической остановкой.
- Batch и streaming на одном префиксе дают те же признаки и прогноз с заявленным float tolerance.
- Пустая история, invalid GPS, unknown unit, out-of-order, stale, отсутствующий cur_dev и no_target обрабатываются явно.
- Fit preprocessing не видит held-out строки; manifest подтверждает группы/время/семейства.
- Submission после повторного чтения: UTF-8, `;`, две колонки, все 151 ID, без дублей/NaN/inf, сохранён знак.

Предлагаемые артефакты (их ещё нужно создать): `model_card.md`, `metrics.json`, `split_manifest.csv`, `features_schema.json`, `training_config`, сохранённая модель, таблица абляций, checksum submission и модели, replay-сценарий с alert lead time. Документировать окружение и рабочие команды только после реализации.

Для демо: показать известное размеченное событие; запустить replay до T; продемонстрировать прогноз цели через 10–15 минут; затем продолжить replay до фактического исхода и показать ошибку. Выбор яркого примера допустим, если рядом есть общая метрика и явно указано, что это демонстрационный кейс. Отдельно показать stale/reconnect и честную деградацию. «Предупреждение за 12 минут» должно подтверждаться сохранёнными prediction_time, target planned time и моментом первого алерта, а не текстом на слайде.

## 11. Реалистичный порядок на оставшееся время

- **25 сентября:** schemas/anti-leak allowlist, split manifest, E0–E2, единый builder, контракт inference, fallback без cur_dev. Результат — обученная воспроизводимая модель и первый корректный CSV, даже если score пока ниже целевого.
- **26 сентября:** causal replay/live parity, estimated cur_dev при достаточной надёжности, E3–E5, версия winner, валидация минимальной вероятности риска; квантили при запасе времени, модельная карточка и реальные latency измерения.
- **27 сентября до freeze:** подтверждение model+submission версии, сквозное демо, тесты/артефакты и передача команде сдачи. Последний вечер — исправления интеграции и документация; полную смену подхода не начинать.

Самые опасные блокеры: недоказанная timezone-связь, отсутствие истинного cur_dev в NDTP, мало независимых реальных групп, synthetic family leakage, скрытая зависимость от fact schedule, неработающий Docker-модельный путь. Самые выгодные улучшения после P0: качественные causal агрегаты, real/synthetic абляция, честный fallback, наглядные интервалы/качество и воспроизводимое раннее предупреждение. GPU, Transformer, сложный дорожный граф и внешние данные оставить P2 до доказанного выигрыша.

## 12. Итоговое решение и различие горизонтов

Рекомендуемый комплект: CPU CatBoost MAE + единый причинный builder + основной/fallback режим по cur_dev + минимальный калибруемый late-classifier + model card и три честных validation отчёта. Первые улучшения — скорость/стоянки/геометрия, затем вес синтетики; сложная нейросеть не нужна без экспериментального преимущества. Все компоненты и метрики выше предложены; выполнены только чтение источников и диагностический пересчёт baseline/границ labels.

**Два разных времени:** контракт датасета задаёт `planned_horizon = target_time_begin − T` в `(600, 900]`. Фактическое предупреждение имеет `actual_lead = fact_arrival − first_alert_time`. Если `first_alert_time = T`, то `actual_lead = planned_horizon + target_delay_s`; опоздание может вывести его за 15 минут, опережение — сократить ниже 10. Поэтому нельзя обещать одновременно эти два диапазона для всех точек. В CSV строго соблюдать planned horizon; в replay отдельно показать распределение actual lead, долю своевременных алертов, recall задержек, false alerts и отсутствие алертов после факта. Actual lead считается только для ретроспективной оценки с labels, не используется как inference-признак. В презентации явно обозначить неоднозначность между формулировкой PDF «до события» и формальным контрактом данных.
