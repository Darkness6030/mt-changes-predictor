  Пересечений `(tr_id, target_stop_id)` между их разметками также нет.
- Все целевые ключи `(tr_id, target_stop_id)` найдены в соответствующем расписании;
  ключ `(tr_id, tt_action_item_id)` там уникален. Это ID планового посещения,

- В расписании 847 уникальных строк `geom`; это ещё не проверенный граф маршрутов.

- `unit_id` и `tr_id` различаются; в каждом CSV один `unit_id` связан с одним `tr_id`.

### 2.2. Пересечения и честность

**Test и validate телеметрия побайтово идентичны.** SHA-256 обоих файлов:
`3c74bb9d3cc5e076a2e7f89de7e78fb103c350757d16c9d629de651ee09bf517`.

`validate/schedule_plan.csv` полностью совпадает с `test/schedule.csv`, если удалить
`time_fact_begin` и оставить колонки validate.

Следствие: это не независимый тест на следующий день или новые ТС. Фактическое время

в inference-признаках; не восстанавливать validate-target через любые join, формулы

## 3. Архитектура MVP

Реализованный стек: Python 3.12+, CatBoost, pandas/NumPy, FastAPI и
React/Vite/TypeScript/Leaflet. PyTorch и GPU добавлять только при подтверждённой пользе.

```text
CSV replay ───┐
             ├─> нормализованные события ─> состояние ТС ─> общие признаки на T
NDTP TCP ────┘                                                │
План расписания + unit_id→tr_id ───────────────────────────────┤
                                                              v
                                                      отдельный ML-модуль
                                                              │
                                                       Backend API → UI
```

Фактическая структура:

- `ml/src/transport_ml/`: data, features, model, training, submission, CLI — реализованы.
- `ml/tests/`, `ml/reports/`, `ml/pretrained/`: тесты, отчёты v1/v2/holdout и готовые комплекты.
- `backend/src/transport_backend/`: NDTP, state, clock, replay, hints, API и оркестрация.
- `frontend/src/`: карта, очередь, карточка, системная панель и адаптивные стили.
- `compose.yaml`: отдельные ML/Backend/UI, профили trainer/replayer/emulator.
- `artifacts/`: локальные модели, предикты и полные результаты, исключены из Git.
- `docs/`: правила, план, исследования и фактический прогресс.

Backend импортирует FeatureBuilder из `transport_ml`, а не писать вторую версию.

Backend не обучает модель в HTTP-запросе. ML-модуль имеет собственный контракт:
вход — признаки, T и целевое посещение; выход — signed `delay_s`, версия модели,
качество входа и, при наличии проверенной калибровки, вероятность опоздания.
PDF требует систему из трёх модулей и отдельно подчёркивает «не монолит».
Поэтому финальная поставка: отдельные ML inference service, Backend и UI, запускаемые
через Docker Compose; обучение — отдельная команда. Локальный вызов Python-модуля
допустим только на промежуточном этапе отладки до выделения сервиса.

Рабочие endpoints: `/health/live`, `/health/ready`, `/api/v1/snapshot`,
`/api/v1/vehicles/{tr_id}`, `/api/v1/predictions`, `/api/v1/alerts`, `/api/v1/status`,
`/api/v1/metrics`, `/api/v1/metrics/quality` и POST-команды replay/ack.
UI использует polling, SSE не реализован. Полный контракт — [API_CONTRACT](API_CONTRACT.md).
В прогнозах есть время данных, T, целевой план, горизонт, задержка и stale-флаг.

### Этап B — 26 сентября, утро: первая обученная модель [P0]

1. Обучить CatBoost-регрессию с MAE на causal-признаках; сравнить прямой target и residual
   `target_delay_s − cur_dev_s`. Для residual на выходе вернуть `cur_dev_s + residual`.
2. Первые признаки: `cur_dev_s`, горизонт, час/день, последнее валидное состояние,
   возраст события, число событий, доля невалидных GPS, скорость и её изменение,
   статистики окон 1/3/5/10 минут, длительность наблюдаемой остановки, расстояние
   до целевой точки и геометрия ближайших плановых посещений.
3. Признаки простоя считать по времени и наблюдениям, не превращать отсутствие данных
   в стоянку. Не использовать будущую точку для интерполяции позиции на T.
4. ID использовать для связей; `sample_id`, packet ID и ID планового посещения исключить
   из model features. Использование `tr_id` сравнить с моделью без него и контролировать
   запоминание; геометрия и время предпочтительнее идентификаторов.
5. Оценить отдельно все train, обычные ID и предполагаемую синтетическую группу.
   Сравнить обучение без синтетики, с ней и с уменьшенными весами синтетических строк.
6. Зафиксировать версии входов, список признаков, seed, параметры, MAE, время fit/predict.

**Готово:** обученный артефакт реально загружается отдельной командой инференса;
сравнение с test baseline 93,3598 с записано. Если улучшения нет — честно зафиксировать,
исследовать признаки и валидацию, не заменять ML вычислением скрытого ответа.

### Этап C — 26 сентября, день: валидация и NDTP [P0]

**ML и проверка обобщения:**

1. Использовать test как предоставленный benchmark, явно отметить его зависимости.
2. Построить дополнительный temporal holdout из доступной разметки: обучающие targets

3. Проверить группировку по ТС и по семействам синтетических копий исходных траекторий.
   Если происхождение синтетики установить нельзя, строгую проверку делать на реальных
   ID, а результат на смешанных данных подписывать как ограниченный.
4. Проверить MAE по ТС, часу, early/ontime/late, горизонту, пропускам и величине задержки.
   Отчёт не должен обещать перенос на другой день по однодневному набору.
5. Выполнить абляции признаков и train-only подбор preprocessing; не подбирать модель
   многократными отправками на validate вместо локального эксперимента.

**Поток:**

1. Реализовать собственный TCP-сервер: эмулятор — клиент, он сам подключается к серверу.
2. Сделать буферизацию кадров по длине NPL, CRC, handshake, Nav00 и известные длины ячеек.
3. Проверить фрагменты TCP, несколько кадров в одном чтении, reconnect, обрезанный кадр,
   ошибочную CRC и неизвестную ячейку. Не угадывать длину неизвестного payload.
4. Нормализовать знаки координат, масштаб 1e7, время, valid flag и unit mapping.
5. Хранить ограниченную историю ТС; одинаковая функция признаков для CSV и live events.
6. Развести event-time replay для офлайн-оценки и реальную обработку только уже принятых
   событий; отдельно измерить влияние поздних пакетов и аномального receive_time.
7. Завести TTL/stale, лимиты буферов, счётчики ошибок и fallback при нехватке истории.

**Готово:** прогноз на одном и том же префиксе событий совпадает в batch и replay;
эмулятор подключается, а перезапуск соединения не роняет сервис.

## 7. Ключевые тесты и риски

| Риск | Проверка / решение |
|---|---|
| Будущая телеметрия улучшает метрику | Изменение/удаление всех событий после T не меняет признаки и прогноз |
| Фактическое расписание протекает через join | Удаление/перестановка `time_fact_begin` не меняет inference-вход; allowlist |
| Разный batch/online | Один префикс событий даёт равные признаки и прогнозы с оговорённой точностью |
| Запоминание синтетических копий | Группировка семейств, real-only отчёт, абляция ID и весов |
| Неверная целевая остановка | Границы +600 исключены, +900 включены; первая плановая остановка окна |
| Пропуски и выбросы | Пустая история/invalid GPS/368 км/ч не вызывают crash и не маскируются |
| CRC, TCP, размеры ячеек | Эталонный кадр, split/coalesced reads, bad CRC, reconnect |
| Случайный поток не идёт по расписанию | Раздельные NDTP smoke test и размеченный CSV replay |
| Невоспроизводимый сабмит | Чистый запуск, сохранённые seed/hash/версии, validator перед отправкой |

Неизвестны timezone CSV, MAE_TARGET и состав финального потока. По уточнениям
организаторов дополнительных данных и боевого эмулятора не будет; участки выделяет
команда, проверка realtime. Не планировать получение невыданного графа как зависимость.
Не отправлять новые вопросы организаторам без инструкции пользователя.
