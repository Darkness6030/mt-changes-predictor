# Исследование проекта: стратегия максимального результата на хакатоне

**Итоговое решение:** сделать законченную систему раннего предупреждения для диспетчера:
обученная модель → причинный поток NDTP → понятный веб-пульт → доказуемые метрики →
повторяемый Docker-запуск. Главный способ повысить шансы на победу — закрыть все критерии
и показать доказательства, а затем улучшать ML и полезные действия диспетчера.

Дата исследования: **25 сентября 2026**. Дедлайн из задания: **27 сентября, 23:59 МСК**.
Рекомендации не гарантируют победу или максимальную оценку. Это историческое исследование
**до реализации**: в момент его написания компонентов ещё не было. Теперь ML v1 реализован;
текущий статус и следующие задачи — в [PROGRESS](PROGRESS.md). Остальной текст фиксирует
исследовательские предложения, а не наличие/отсутствие функций на сегодняшний момент.

| Питч: ответы жюри | 4 | Корректные ответы с доказательствами | Приложения с валидацией, архитектурой и измерениями |

Всего **26 + 10 = 36**. За пределами точности ML остаётся до 30 баллов. Отдельных
гарантированных баллов за GPU, LLM, мобильное приложение, авторизацию или 3D-карту нет.

ML-шкала: ≥0,70 → 6; 0,60–0,69 → 5; 0,50–0,59 → 4; 0,40–0,49 → 3;
0,25–0,39 → 2; 0,10–0,24 → 1; <0,10/нет валидного CSV → 0.
Границы приведены как в PDF, порядок округления не дан.

**Стратегия:** не ставить сквозной запуск и сдачу под угрозу ради небольшого улучшения
leaderboard. Но и baseline-файл не выдавать за готовое ML-решение: организаторы проверяют
потоковую модель и аннулируют нечестно достигнутый лучший score.

## 3. Что говорят данные и чего они не позволяют обещать

| Факт | Следствие для решения |
|---|---|
| Train: 4 434 точки, test: 353, validate: 151 | Малый табличный набор: сначала бустинг, контроль split и короткий поиск |
| 3 293 train-точки с ID 9000000…9000025 — 74,3% | Проверить пользу синтетики и её вес; не считать её независимыми наблюдениями |
| Test/validate traffic полностью одинаковы, планы совпадают после удаления факта | Нельзя добывать validate-ответы из test schedule; test не независимый день |
| Всего 13 обычных ТС с разметкой, основной период — один январский день | Нет доказательства переноса на завтра, другой сезон или весь город |
| Встречаются invalid GPS, пропуски, дубли, 368 км/ч и разрывы на часы | Нужны causal-очистка, freshness, missing flags и отказ/деградация |
| Нет route_id/trip_id/doors/графа/подтверждённых ДТП | Показывать восстановленную схему, не выдумывать маршрут/причину |
| `cur_dev_s` есть в точках, но не в Nav00 | Отдельно решать online-оценку и fallback; одного CSV-score недостаточно |
| CSV без timezone, emulator timestamp — текущие Unix seconds | Часы и историческое replay должны быть явными |

Повторно рассчитанные ориентиры: test MAE нулевого прогноза **103,3371 с**,
`cur_dev_s` **93,3598 с**, train median=24 с **100,8725 с**. В реальной группе train
(рабочее выделение ID<9M) 1 141 строка и MAE `cur_dev_s` **86,8379 с**.
Это baseline, не достигнутое качество будущей модели. [Детали диагностики](research-ml.md).

При положительном знаменателе платформенной формулы score ≥0,70 означает:

```text
MAE <= 0.30 × mae_zero + 0.70 × MAE_TARGET
```

Скрытые `mae_zero` и MAE_TARGET неизвестны. Нельзя вывести честную точную цель в секундах
из локального test и приблизительного baseline score≈0,40.

## 4. Выбранный стек и границы компонентов

| Часть | Решение | Почему сейчас |
|---|---|---|
| ML | Python 3.12+, CatBoost CPU, pandas/NumPy, scikit-learn | Табличные признаки, мало labels, прямой MAE, простая поставка |
| Backend | FastAPI + Pydantic, asyncio TCP, HTTP-клиент к ML | API/Swagger, NDTP ingestion и управление состоянием |
| ML service | Отдельный Python HTTP-сервис с загруженной моделью | Изолированный inference-контракт, нет обучения в HTTP-запросе |
| Frontend | React + Vite + TypeScript, Leaflet, простой CSS | Один интерактивный экран, карта и контролируемые состояния |
| UI delivery | Production-статика и reverse proxy, отдельный контейнер | Единый origin, API за proxy, не dev-server |
| Live updates | Snapshot polling 1 с на старте; SSE при необходимости | Быстрая интеграция, переход по результатам замера latency |
| State | Ограниченные in-memory окна в одном ingest-процессе, сохраняемый audit | Не вводить Kafka/Redis без причины; явно ограничить масштаб MVP |
| Поставка | Docker Compose: UI / Backend / ML; профили replay и emulator | Один воспроизводимый запуск и понятная демонстрация трёх модулей |
| Качество | pytest, schema checks, split manifests, model card, benchmark reports | Проверять существенные свойства и показывать результат жюри |

Версии фиксировать при реализации lockfiles/образами после проверки совместимости.
Не переносить номер текущей веб-документации в зависимости без проверки среды.

Почему не Next.js/Streamlit для финального экрана: SSR/SEO не закрывают дополнительный
критерий диспетчерского приложения; управляемый map/list/card UI здесь важнее notebook-подачи.
MapLibre полезен для богатой векторной карты, но вносит дополнительные style/tile/font assets.
Это выбор для данного срока и объёма, не утверждение, что другие технологии хуже вообще.
[Сравнение и первичные источники](research-frontend.md#2-сравнение-технологий).

Vite предназначен для сборки статики; `vite preview` не использовать как production server.
[Vite: static deployment](https://vite.dev/guide/static-deploy.html).
CatBoost поддерживает MAE и quantile objectives — это основание для выбранного пути.
[CatBoost: regression losses](https://catboost.ai/docs/en/concepts/loss-functions-regression).

### Согласованное владение данными

```text
CSV replay / NDTP TCP
          │
          v
Backend: normalizer → state → plan matching → FeatureBuilder
          │                                   │
          │                          общая Python-библиотека
          │                          используется и в offline train
          v
ML service: versioned features → delay + probability + model metadata
          │
          v
Backend: alerts + snapshot + audit → UI: queue / map / incident
```

- Backend владеет clock, состоянием, планом, mapping, выбором target, quality и алертами.
- FeatureBuilder — один общий модуль; batch и live не переписывают логику по отдельности.
- ML принимает типизированные признаки нужной версии; возвращает прогноз, не выбирает
  произвольно другую цель и не читает фактическое расписание.
- UI отображает состояние и выполняет действия интерфейса; не рассчитывает target,
  вероятность, ML-признаки или интерпретацию timezone в JavaScript.
- Обучение — отдельная команда; production-start загружает готовую модель.

## 6. ML: что и в каком порядке делать

### Признаки, которые доступны на момент T

1. `cur_dev_s` с missing/source/age; разность планового target и T.
2. Последняя валидная скорость, статистики за 1/3/5/10 минут, изменение короткого/длинного окна.
3. Наблюдаемая стоянка и доля низкой скорости; большие gaps не считать часами простоя.
4. Расстояние по прямой до целевой точки, направление к ней, плановые интервалы.
5. Возраст события и GPS, число наблюдений, доля invalid, span истории и пропуски.
6. Время суток после фиксации timezone; день недели на одном дне не доказанный сигнал.
7. После основы: причинный прогресс по плану и наблюдаемый контекст соседних ТС.

Не использовать sample/packet/target ID для запоминания ответов, `time_fact_begin`,
`target_class`, будущий GPS, centered rolling или заполнение из будущего.
Плановое будущее разрешено; фактическое будущее запрещено.

### `cur_dev_s` — отдельная задача, а не готовое поле потока

Для batch подсказка разрешена. Для NDTP оценивать пройденное посещение по плану,
последовательности, геозоне и уже полученным наблюдениям. Подтверждение прибытия может
появиться позже самого прибытия: хранить `available_at`, а не задним числом менять прогноз.
При неоднозначности/нет истории — missing и проверенная модель без подсказки.

Сравнивать MAE и coverage в трёх режимах: provided / estimated / missing. Ни одна онлайн
демонстрация не должна незаметно подставлять `cur_dev_s` из будущей прогнозной точки CSV.

### Эксперименты и критерий принятия

| Порядок | Проверка | Решение |
|---|---|---|
| E0 | Ноль, медиана train, cur_dev, causal-tests | Зафиксировать baseline и split до tuning |
| E1 | Неглубокий CatBoost MAE на минимальных признаках | Получить реальную загружаемую модель |
| E2 | Скорость/стоянки/геометрия | Оставить блок при устойчивом real-holdout улучшении |
| E3 | Direct target против residual к cur_dev | Сравнить также missing/estimated режим |
| E4 | Synthetic weight 0 / 0,25 / 1 | Выбор по реальным данным и группам, не train MAE |
| E5 | Прогресс/соседи/малый ensemble | Не принимать выигрыш ценой утечки и сломанной parity |
| E6 | Late classifier + calibration | Обязательный продуктовый выход после регрессии |
| E7 | Квантили/интервалы | P1, только с проверкой покрытия и crossing |

Три отчёта: организаторский test, real-only temporal и group robustness. Синтетические
семейства не разделять между train/holdout; если происхождение неизвестно — строгую
оценку строить на реальных ID и прямо сообщать ограничение. Purge учитывать по доступности
исхода, а не просто вычесть 15 минут: позднее фактическое прибытие может быть ещё неизвестно.
[Подробный протокол](research-ml.md#6-честная-валидация).

Для late classifier target `delay > 120 с`; границы −60/+120 в имеющихся labels относятся
к ontime. Проверить всю разметку. Использовать temporal/group calibration без случайного
CV; показывать Brier/log loss, reliability bins и число наблюдений. Один низкий Brier не
доказывает калибровку. [scikit-learn: calibration](https://scikit-learn.org/stable/modules/calibration.html).

Квантили и SHAP не превращать в подтверждённую физическую причину. Общий MAE не является
интервалом ошибки отдельного автобуса. Если вероятность недостаточно проверена — явно
обозначить качество либо временно убрать процент; это ограничение полной поставки.

## 7. Backend, NDTP, часы и надёжность

NDTP — клиентский эмулятор подключается к серверу команды. TCP-чтение не равно пакету.
Кадр NPL(15) + NPH(10) + тело; `dataSize` относится к NPH+телу. Packed little-endian;
CRC-16/Modbus по NPH+телу, поле CRC со swapped bytes. У ячеек type/number нет общей
длины payload: неизвестный type нельзя пропускать по догадке. Nav00 несёт координаты
/1e7, hemisphere bits, valid, timestamp, speed. `unit_id` нужно сопоставить с `tr_id`.
[Исходная спецификация](../dataset/docs/Emulator-and-Telematic-Packets-Specification.md).

### Три времени и два разных горизонта

- **Source/event time:** дата телеметрии и cutoff T.
- **Simulation clock:** управляет историческим replay и возрастом его данных.
- **Wall/monotonic time:** сеть, таймауты и время вычисления/доставки.

`planned_horizon_s = target_plan − T` должен быть в `(600,900]`.
`actual_arrival_lead_s = actual_arrival − first_alert_as_of` измеряется ретроспективно.
Если алерт создан в T, actual lead = planned horizon + target delay. Позднее прибытие
может дать более 15 минут до факта, раннее — менее 10. Не обещать оба окна одновременно;
уточнить у организаторов трактовку, сохраняя точный контракт CSV.

Timestamp официального эмулятора всегда текущий; автогенерация не движется по январскому
расписанию. Нужны **два честно подписанных сценария**, а не скрытый сдвиг дат:

1. Официальный эмулятор → настоящий TCP parser → UI: приём, нормализация, ошибки и reconnect.
2. Исторический causal replay → тот же state/features/ML → алерты: качество и горизонт.

Для наиболее убедительной сквозной демонстрации добавить controlled CSV→NDTP replay,
сохраняя исходный timestamp и virtual clock; сравнить его с обычным CSV adapter.
Он не заменяет smoke-test официального эмулятора. Nav00 хранит секунды и целочисленную
скорость: CSV→NDTP может терять наносекунды, точность координат и дробные значения.
Паритет бинарного decoder проверять с каноническим **квантованным** входом; точный CSV
replay и расчёт submission оставлять отдельными, а разницу метрик после квантования измерить.
Неизвестную timezone сначала определить;
не менять её молча ради совпадения сценариев.

### Согласованный API-контракт

Эндпоинты ниже — целевой договор, а не уже работающий API:

| Endpoint | Контракт |
|---|---|
| `GET /api/v1/snapshot` | run_id, revision, mode, clock, vehicles, alerts, status |
| `GET /api/v1/vehicles/{tr_id}` | Текущая цель, план/прошлый track, прогнозы, evidence |
| `GET /api/v1/status` | Health, состояние модели/приёмника, фактические метрики |
| `POST /api/v1/replay/control` | Demo-only start/pause/reset/speed, новый run при reset |
| `POST /api/v1/alerts/{alert_id}/ack` | P1: идемпотентная отметка принятия к работе |
| `GET /api/v1/events` | P1 SSE с revision и resync snapshot после разрыва |

В prediction обязательны `prediction_id`, `model_version`, `feature_schema_version`,
`cutoff_T`, `computed_at`, `target_stop_id`, `target_planned_at`, `horizon_s`, `delay_s`,
`prediction_status`, `cur_dev_source`, качество данных. `late_probability` nullable
с причиной отсутствия; `interval` только при проверенной модели интервалов.
Идентификаторы передавать строками; точное время не округлять ради UI. OpenAPI Backend —
единственный источник схем; локальные варианты имён в подробных исследованиях привести к нему.

Без цели/истории/маппинга возвращать `no_target / insufficient_history / unmapped`,
а не нулевой «успешный» прогноз. Версия старого ответа не должна перезаписать новый snapshot.
Пауза replay не делает данные stale по wall clock, но потеря API по wall clock видна всегда.

### Приёмка надёжности

Ограниченные очереди/окна, счётчики потерь/ошибок, таймаут ML, явный degraded mode;
один владелец ingest state, без случайного дублирования через несколько web workers.
Проверить перезапуск NDTP, ML и Backend по отдельности. Fallback маркировать вместе с
источником, последняя позиция сохраняет реальный возраст.

В Compose одного `depends_on` недостаточно: контейнер running ещё не означает ready.
Использовать healthcheck/readiness и `service_healthy` где нужна готовность, плюс runtime
retry/reconnect. [Docker: startup order](https://docs.docker.com/compose/how-tos/startup-order/).

Замеры: N событий/ТС, частота, hardware/OS/CPU/RAM, версия модели, p50/p95 inference,
полный event→UI, throughput, длина очереди и cold start. PDF даёт ориентир инференса
<1–2 с на поток; это не измеренный результат нашего проекта. Polling 1 с входит в
полную задержку доставки, поэтому при необходимости перейти на SSE.

## 8. Как должен выглядеть фронтенд

**Основной формат — desktop web для диспетчера**, проверка на 1366×768 и большем экране.

```text
┌ Название ─ LIVE/REPLAY ─ Время источника ─ Связь ─ Сводка ┐
│ Очередь проблем   │ Карта Москвы          │ Карточка ТС   │
│ +3:10 через 12 м  │ ТС и выбранная цель   │ План / ETA    │
│ Фильтры / поиск   │ Схема / прошлый трек  │ Риск / данные │
│ Нет данных       │ Легенда / масштаб     │ Что проверить │
└──────────────────┴───────────────────────┴───────────────┘
```

Очередь отвечает «что требует внимания», карта — «где», карточка — «когда, насколько и
что можно сделать». Выбор связан между списком и картой, обновления не сбрасывают фокус
и не прыгают к новому центру. Технические model IDs и Swagger — в панели «Система».

В карточке: signed delay крупно; план и ожидаемое прибытие; T и плановый горизонт;
вероятность с честным качеством; источник/возраст данных; наблюдаемые паттерны; рекомендация.
Фраза «ТС скоро опоздает» без конкретного target и времени недостаточна.

Три разных понятия:

- **severity:** величина/категория отклонения, определяемая продуктовой политикой;
- **probability:** оценка классификатора, не линейное преобразование delay;
- **freshness/quality:** можно ли доверять входным данным и актуален ли прогноз.

Пороги severity согласовать до кода и показывать в легенде. Предложение frontend:
зелёный −60…+60 с, жёлтый +60…+120 или опережение <−60, красный >120. Это внутренний
уровень внимания, не официальные target_class (ontime в labels включает +120).
Stale/unknown имеют отдельный badge/серый стиль; отсутствие прогноза не зелёное.
Цвет дублировать текстом/знаком. [WCAG: use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

Действие «Принято в работу» — acknowledgment, не команда выпуска резервного автобуса
и не доказательство устранения задержки. Нет подтверждённых ДТП/поломок — нет таких
утверждений. Причину описывать как гипотезу, evidence — как наблюдение.

### Карта и резерв без интернета

Входных маршрутов нет: показать «Схему плановых посещений» и «Наблюдавшийся трек»;
будущие GPS не рисовать. Географические координаты WKT/GeoJSON — lon,lat, Leaflet — lat,lon.
Не соединять суточный список посещений в якобы официальный маршрут без проверки рейсов.

Для небольшого online-демо стандартные OSM tiles требуют видимой атрибуции и соблюдения
policy; нельзя массово скачать город/zoom levels для offline. Резерв — собственные
точки/линии без подложки с подписью, локальные шрифты/иконки и запись демо. Полноценная
offline-карта требует разрешённого источника или собственного сервера.
[OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/).

## 10. Как организовать реализацию без распыления

Оценки времени в подробных отчётах — человеко-часы, не календарный срок и не обязательства.
Предварительные оценки: Backend P0 20–30 ч; frontend с выводом вероятности 13–20 ч;
ML-эксперименты имеют открытый бюджет, потому что качество заранее неизвестно. Эти часы
не складывать в обещание, что всё успеет один разработчик до дедлайна.
Число разработчиков неизвестно; ML/backend/frontend можно вести параллельно после контракта.
Три субагента исследовали части, но это не означает, что разработка уже выполнена.

1. **Gate A — договор и данные.** Схемы/clock/target/FeatureBuilder, запрет фактов, split,
   baseline и validator. Одновременно frontend на явно обозначенных dev-fixtures.
2. **Gate B — минимальный сквозной поток.** Маленькая настоящая модель + NDTP + ML API +
   snapshot + карта. Не ждать лучшей модели, чтобы обнаружить интеграционные ошибки.
3. **Gate C — функциональная полнота.** cur_dev fallback/оценка, classifier probability,
   ранняя карточка, Docker, reconnect. Категории риска без модели — промежуточное состояние.
4. **Gate D — выигрыш и доказательства.** Feature абляции, synthetic weights, удобство UI,
   замеры, протоколы причинности, документация и выбранный демонстрационный сценарий.
5. **Gate E — freeze и сдача.** До 27 сентября 16:00 выбрать устойчивую версию; до 22:30
   иметь готовые обе сдачи и проверенный доступ. Это внутренние ориентиры, официальный
   дедлайн — 23:59. Последний вечер не менять архитектуру/модельный подход.

Останавливать новую фичу, если она не успевает пройти интеграцию, проверку и репетицию.
Два последовательных ML-улучшения без устойчивого real-holdout выигрыша — повод вернуть
ресурс интерфейсу, надёжности и защите. Не мерить успех количеством моделей и экранов.

## 11. Матрица окончательной приёмки

| Проверка | Что считается подтверждением |
|---|---|
| Cutoff / антиутечка | Подмена будущих событий и fact columns не меняет текущий прогноз |
| Feature parity | Batch/replay на одинаковом префиксе совпадают; NDTP сравнивается с квантованным эталоном |
| Цель | +600 исключено, +900 включено; первая плановая цель, правильное посещение |
| Вероятность | Отдельный classifier, holdout, reliability bins/N; не нарисованный процент |
| Входные аномалии | Unknown unit, empty history, invalid GPS, repeats и stale не скрываются |
| NDTP | CRC, неполный/склеенный кадр, неизвестный type, reconnect проверены |
| UI | За 5 секунд понятно ТС/место/ожидание; выбор и карточка работают при обновлении |
| Режимы/часы | Replay явно подписан, pause/reset не смешивают runs и age/health clocks |
| Надёжность | NDTP/ML/API сбои демонстрируются; recovery не создаёт дублей/старых ответов |
| Производительность | N/hardware/config/version + p50/p95 + очередь + cold start |
| Сдача | CSV принят, форма сохранена, ссылки и Docker проверены не только владельцем |

Не объявлять пункты пройденными на основании документации. Сохранять реальные результаты
проверок в PROGRESS/отчётах по мере реализации.

## 12. Защита, которая поддерживает продукт

Подготовить демонстрационное ядро примерно на 4 минуты (длительность питча в локальных
материалах не задана): проблема → очередь риска → выбранное ТС/цель/время → evidence и
действие → ML vs baseline → обрыв/восстановление → измерения и ограничения.

В интерфейсе доказать сразу четыре вещи: предупреждение появилось до события; источник
данных и clocks понятны; прогноз дала модель; оператор понимает следующий шаг.
Выбранный яркий пример сопровождается общими метриками, а не заменяет их.

Слайды: пользовательская проблема; сценарий; три модуля; честные метрики; надёжность;
ограничения и пилот. В запасе — split/абляции/cur_dev/latency. Не обещать экономию денег
или сокращение реальных задержек без пилота: сейчас доказуемы качество прогноза,
время предупреждения, скорость обработки и понятность интерфейса.

Ключевые ответы: «откуда cur_dev в live», «почему нет утечки», «что значит 80%»,
«где настоящий маршрут», «что при потере связи», «почему январь при живом NDTP»,
«сможет ли жюри запустить без вас». [Разбор ответов](research-competition.md#8-вопросы-которые-нужно-уметь-закрыть).

## 13. Неопределённости и границы исследования

Нужно уточнить у организаторов: timezone; planned-vs-actual трактовку горизонта;
источник плана/mapping/cur_dev в live-проверке; обещанный граф/эталон; MAE_TARGET и
округление; длительность защиты и формат доступа жюри. Вопросы не отправлялись.

Не проверены runtime: импорт эмулятора и ARM execution, Docker-build, совместимость
зафиксированных будущих зависимостей, ML-качество новых моделей, достижимая latency,
калибровка и фактическая удобность экрана. Исследование даёт способы проверки, а не их результаты.

Согласованные решения при различиях между отчётами: минимальная вероятность — P0 полной
поставки; polling — стартовый транспорт с измерением, SSE — по бюджету latency;
Backend строит признаки общим модулем, ML сервис только инференс; API префикс `/api/v1`;
плановый и фактический lead time раздельны; маршруты/причины явно помечены по происхождению.
