# Реализованные возможности: что, как и зачем

Срез 27.09.2026, ветка `claude/jolly-noether-9yp4y4`. Запуск и сценарии проверки —
[DEMO.md](DEMO.md), измерения — [PERFORMANCE.md](PERFORMANCE.md), ML — [отчёт v4/v5](../ml/reports/ml-v5.md),
контракт API — [API_CONTRACT.md](API_CONTRACT.md). Всё ниже работает на потоке NDTP и на

## 1. Дополнительные фичи из PDF

| Фича PDF | Статус | Как сделано | Зачем |
|---|---|---|---|
| **What-if «выпуск дополнительного ТС»** | Реализовано | `GET /api/v1/vehicles/{id}/whatif?reserve_in_min=N`, блок в карточке. Прогнозная задержка доходит до конца рейса; отстой на конечной сверх 3 мин её гасит, остаток переходит на следующий рейс; резерв, прибывший на конечную через N мин, берёт первый рейс, где уйдёт раньше опаздывающего ТС. Ответ: рейсы «без/с резервом», сколько рейсов с опозданием > 2 мин удаётся избежать, допущения | Диспетчер до выпуска резерва видит, поможет ли он: часто отстой сам гасит опоздание — и система честно пишет «резерв не нужен» |
| **Ансамбли моделей** | Реализовано: CatBoost; CatBoost + PyTorch проверен и отклонён | Основная регрессия — ансамбль 3 CatBoost с подсказкой `cur_dev_s`, автономная — ансамбль 3 CatBoost без неё; маршрутизация main/fallback по наличию подсказки; отдельные классификаторы вероятности. Ансамбль с нейросетью PyTorch (GRU по последним 10 мин телеметрии до T + MLP по 73 признакам, `ml/experiments/improve18_sequence.py`) обучен по тому же протоколу: сама сеть 95.7 с против 76.0 у CatBoost (внутр. фолды), лучшая смесь для основной модели — вес CatBoost 1,0; для автономной внутри −0,15 с, но на отложенных ТС хуже (73.56 → 73.70 с). В модель не включён | Точность (score 0,86126) и работа в потоке, где подсказки нет. Нейросеть честно проверена: на 1,5 тыс. размеченных точек одного дня она не добавляет информации сверх признаков |
| **Map Matching с учётом NDTP** | Реализовано базово, усложнение проверено и отклонено | Привязка GPS к плановой последовательности посещений ТС: причинное окно, радиус 60 м, середина стоянки; фильтр подменённых GNSS-фиксов по признакам потока (зона у Шереметьево, скачки, правдоподобие скорости) — `transport_ml.gps_trust`; отметки времени NDTP целыми секундами | Корректная позиция на карте, текущее отклонение по GPS, паспорт предупреждения. Последовательный матчинг с интерполяцией прохождений не улучшил согласие с эталонным `cur_dev_s` (MAE 62,5 → 64,0 с на train) и не внедрён |
| **Оптимизация инференса** | Реализовано: ONNX Runtime | `ML_RUNTIME=onnx` (default): модели v5 при старте экспортируются в ONNX и исполняются ONNX Runtime; загрузка проверяет паритет с CatBoost (≤ 8e−05 с; при расхождении — автоматический возврат на CatBoost с причиной в `/v1/model`). Одиночный запрос 8,9 → 1,8 мс (×4,8), пакет 32 — ×2,8. SHAP не считается в потоковом цикле, только по запросу карточки с кэшем (56/99 → 8,9/14,4 мс). TensorRT/GPU не нужны | Ориентир PDF < 1–2 с выполнен с запасом на три порядка; меньше CPU на прогноз — больше ТС на один сервис |

## 2. Функции для диспетчера

| Функция | Как | Зачем |
|---|---|---|
| **Очередь «требуют внимания»** | Задержка вне коридора (> 60 с опоздания или > 60 с опережения) **или** вероятность опоздания > 120 с не ниже 50 %; основание видно бейджем | Не пропустить ТС, которое по вероятности опоздает, хотя средний прогноз ещё в норме |
| **Первый и последний рейс дня** | Рейсы восстановлены из плана (ID рейсов в данных нет): граница — разворот на конечной (возврат в точку ≤ 60 м через 1–3 посещения) или перерыв > 30 мин. Бейдж, приоритет в очереди, плитка «крайние рейсы в риске», рекомендация | По Q&A срыв крайних рейсов критичен для выполнения плана перевозок |
| **Паспорт предупреждения** | Для каждого алерта — первое предупреждение и за сколько минут до плана, тренд прогноза; после прибытия — факт по полученным GPS-точкам (без разметки) и исход: подтвердилось / в норме / в другую сторону. Сводка `early_warning` | Доказывает раннее предупреждение **на потоке**: не «задним числом», за сколько минут до события предупредили |
| **«Из чего сложился прогноз»** | SHAP-вклады CatBoost, взвешенные по ансамблю и сгруппированные (подсказка, положение по GPS, стоянки, скорость, путь до цели, время/место, качество данных); сумма = прогноз | Понятное основание прогноза без выдуманных причин: данных о ДТП нет, это арифметика модели |
| **«Где копится опоздание»** | Прирост отклонения между соседними наблюдаемыми по GPS остановками, накопленный за прогон; топ отрезков над очередью | Видны проблемные участки, где систематически теряется время |
| **Конкретные рекомендации** | По ситуации: крайний рейс — приоритет и резерв; вероятное опоздание — заранее уточнить обстановку; опережение — «придержать на ~N мин»; устаревшая позиция — проверить связь с терминалом | Предложение действий (по Q&A «очень желательно») |
| **«Принято в работу»** | Отметка покрывает открытые алерты ТС и переносится на следующие остановки эпизода (до 15 мин) | Диспетчера не переспрашивают о той же машине на каждой остановке |
| **Подмена GPS** | Фильтр `gps_trust`: фиксы в зоне подмены у Шереметьево, скачки > 1 км со скоростью > 150 км/ч скрываются с карты, показывается последняя достоверная позиция с флагом | В данных 6 ТС «стояли» на аэродроме из-за GNSS-спуфинга |
| **Мобильный вид** | На экране ≤ 640 px — вкладки «Очередь / Карта / ТС / Система» с числом ТС, требующих внимания; выбор ТС в очереди открывает карточку, «показать на карте» — карту; KPI прокручиваются строкой. Манифест PWA: пульт ставится на главный экран телефона | Диспетчер или начальник колонны видит ситуацию не только за пультом |
| **Вход и роли** (опционально) | `BACKEND_AUTH_USERS`: диспетчер (отмечает алерты, управляет источником) и наблюдатель (только просмотр); токен Bearer, в UI — форма входа, имя в шапке и в отметке «принял: …». По умолчанию выключен, чтобы жюри открыло стенд без учётных записей | Ответственность за реакцию на алерт и безопасный показ на общем табло |
| **Честная деградация** | Отказ ML — последний прогноз с возрастом и баннер; обрыв NDTP — статус устаревших данных и восстановление; нет прогноза — статус вместо нуля | Диспетчер не принимает старое за актуальное |

## 3. Инженерные свойства

- **Три независимых модуля** в Docker: ML-сервис (FastAPI + CatBoost), Backend (NDTP TCP,
  состояние, API), UI (React/Vite/nginx). Запуск: `docker compose up -d --build --wait`;
  проверен из чистого клона (healthy за 1 мин 38 с).
- **NDTP**: разбор кадров по спецификации, CRC, дробление/склейка TCP, переподключение;
  отправитель-реплеер с повтором и кодом выхода. 56 тыс. кадров без ошибок CRC.
- **Дата живого потока**: расписание автоматически сдвигается на целые сутки к дате потока.
- **Причинность**: только события `event_time ≤ T`, факты расписания не читаются кодом
  признаков, синтетика и ответы validate не используются (проверено тестами и аудитом).
- **OpenAPI**: типизированные ответы Backend в Swagger (`/docs`), ML — `/v1/predict`,
  `/v1/model`; документация кода — Sphinx (`docs/sphinx`, сборка без предупреждений).
- **Тесты**: 190+ (признаки, причинность, NDTP, состояние, движок, API, what-if, паспорт).
