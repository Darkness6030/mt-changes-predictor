## 4. Производительность и дополнительные возможности — текст для вставки

```text
Решение — рабочая система раннего предупреждения о задержках, а не только модель в ноутбуке.
Три независимых Docker-модуля поднимаются одной командой docker compose up:
• ML-ядро (FastAPI, CatBoost + ONNX Runtime) — прогноз задержки, вероятность опоздания,
  объяснение прогноза; модель в HTTP не обучается, версия и качество публикуются в /v1/model;
• Backend — приём телеметрии NDTP по TCP (кадрирование, CRC, переподключение), состояние
  парка, причинные признаки, инциденты и API диспетчера;
• BI-дашборд (React + Яндекс Карты) — очередь внимания, карта, карточка ТС, системная панель.

КАЧЕСТВО ПРОГНОЗА
Модель v8 даёт score платформы около 0,95 (MAE-прогноз signed задержки за 10–15 минут).
Это два ансамбля по шесть CatBoost (с текущим отклонением cur_dev_s и автономный — для потока
без подсказки) на 82 причинных признаках и обучаемый гейт «задержка ровно 0».
Путь 0,70 → 0,86 → 0,90 → ≈0,95 получен только честными шагами:
• признаки структуры рейса по плановому расписанию: отстой на конечной «гасит» накопленное
  опоздание (корреляция cur_dev_s с целью падает с 0,68 до ~0), модель это теперь видит;
• ансамбль двух независимо отобранных моделей вместо одной (0,86 → 0,90);
• hurdle-гейт: классификатор P(задержка = 0) на тех же признаках; при P > 0,5 прогноз 0 —
  это условная медиана, оптимальная для MAE (порог из теории, не подобран под скор).
  Проверка без test в обучении: из обнулённых точек 95,8% действительно ровно 0.
Честность данных проверена и зафиксирована: признаки используют только телеметрию с
event_time ≤ T, будущий план и cur_dev_s; факты расписания и metadata факта (manual_fill)
не читаются. Синтетические ТС train оказались сдвинутыми копиями реальных ТС того же дня —
их копии моментов validate удаляются перед обучением, иначе это утечка ответов.
Потоковый режим подтверждён: Backend, получая телеметрию validate потоком, выдал через
ML-сервис те же прогнозы, что в CSV, — 139 из 139 числовых (медиана расхождения 8e−06 с,
максимум 0,023 с); ещё 12 точек честно помечены «данные устарели» (терминал передавал
location_valid=false), число не выдумывается (docs/stream-csv-parity.json).

ПРОИЗВОДИТЕЛЬНОСТЬ
Инференс v8 (12 регрессоров + гейт + 2 классификатора), готовые признаки validate,
300 повторов, Linux x86_64, 1 поток: ONNX Runtime против CatBoost p50/p95 —
batch 1: 6,15/7,13 мс против 19,65/28,02 мс (в 3,2 раза быстрее);
batch 8: 7,99/10,20 против 19,41/28,88 мс; batch 32: 11,10/13,75 против 20,07/30,78 мс.
Расхождение ONNX с CatBoost ≤ 9,1e−05 с; сервис включает ONNX только после стартовой
проверки совпадения и иначе сам возвращается к CatBoost (причина видна в /v1/model).
Сквозной замер цепочки в Docker (NDTP-replay 60×, 512 измерений, на предыдущей
модели v5, p50/p95): ML-инференс 8,92/14,35 мс; Backend → ML → Backend 15,21/22,77 мс;
признаки 42,26/65,02 мс; от приёма события до публикации прогноза 172/317 мс, включая
такт Backend 0,5 с. 29 532 NDTP-кадра — 0 ошибок CRC, 0 битых кадров; переподключение и
восстановление после остановки ML проверены. За ~30 минут потока память Backend
137 → 139 МиБ, ML 84 → 85,5 МиБ: состояние и буферы ограничены. Чистый клон без .env
поднимается в три healthy-сервиса. Ограничение: многочасовой нагрузочный тест не проводился.

ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ
• Вероятность опоздания > 120 с с Platt-калибровкой (вне фолдов: Brier 0,1065 против
  0,1843 у базовой частоты, ROC-AUC 0,895).
• Объяснение каждого прогноза (SHAP): вклад групп признаков в секундах — подсказка,
  отстой на конечной, движение, путь до остановки, свежесть данных; сумма = прогноз.
• Паспорт предупреждения: когда система впервые предупредила, как менялся прогноз,
  что произошло фактически и какое реальное упреждение получил диспетчер.
• What-if «выпуск резервного ТС» на линию с открыто показанными допущениями.
• «Где копится опоздание» — проблемные участки по наблюдаемым прохождениям остановок.
• Приоритет первого/последнего рейса дня, рекомендации диспетчеру, «принято в работу»
  с именем диспетчера и переносом отметки на эпизод ТС.
• Фильтр подменённого GNSS (автобусы «на аэродроме Шереметьево» не попадают на карту).
• Три демо-источника (CSV-replay, NDTP-replay, официальный эмулятор), просмотр истории
  без остановки приёма, автосдвиг даты плана к дате потока, индикация устаревания.
• Мобильный вид с вкладками и установкой на телефон (PWA); опциональный вход с ролями
  диспетчер/наблюдатель (по умолчанию выключен, жюри открывает стенд без входа).
• Полная документация: Sphinx, OpenAPI и Swagger обоих сервисов, воспроизводимые рецепты
  обучения и отчёты по каждой версии модели.

Ограничения, которые мы не скрываем: оценка на одном дне; геометрия маршрута —
схема соседних остановок, а не дорожный граф; итоговая модель обучена на train+test,
поэтому MAE по test в интерфейсе помечен in-sample. Подробно: docs/FEATURES.md,
docs/PERFORMANCE.md, ml/pretrained/v8/README.md.
```
