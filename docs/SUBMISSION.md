## 4. Производительность и дополнительные возможности — текст для вставки

```text
Система состоит из трёх Docker-модулей: ML-ядро (FastAPI + CatBoost), Backend
(приём NDTP по TCP, состояние транспорта, признаки и API), BI-дашборд
(React + Яндекс Карты). Модель v5 использует 73 причинных признака и два ансамбля
по три CatBoost: с текущим отклонением и автономный, для потока без подсказки.

Производительность: в замере Docker/Linux x86_64, NDTP-replay исторической
телеметрии на скорости 60×, p50/p95 по 512 измерениям составили:
• ML-инференс — 8,92/14,35 мс;
• Backend → ML → Backend — 15,21/22,77 мс;
• подготовка признаков — 42,26/65,02 мс;
• цикл Backend — 95,75/149,46 мс;
• приём использованного события → публикация прогноза — 172,32/316,50 мс.
Последняя метрика включает ожидание такта Backend (0,5 с), но не отрисовку
браузера; дашборд опрашивает API раз в секунду. Это замер демонстрационного
потока, не предельная пропускная способность. Накопление очередей отдельно
не измерялось. В сохранённом снимке — 29 532 NDTP-кадра, 0 ошибок CRC,
0 некорректных/обрезанных кадров и 8 закрытий соединений; переподключение
и восстановление после stop/start ML проверены. При недоступности ML Backend
продолжает отвечать и показывает последний прогноз с возрастом данных.

По журналу примерно 30-минутного прогона, при росте счётчика до 56 324 кадров
память Backend изменилась с 137 до 139 МиБ, ML — с 84 до 85,5 МиБ, UI — около
5 МиБ. Многочасовой нагрузочный тест не проводился. Запуск трёх healthy-сервисов
занял 1 мин 38 с в среде автора замера с заранее скачанными образами и адаптацией
сборочного окружения; это не cold start без кеша. Дополнительно 27.09 проверен чистый клон без .env и без изменений Dockerfile:
три сервиса healthy, NDTP → признаки → ML → API работает; в контрольном снимке
6 707 кадров без ошибок CRC/invalid/truncated. Использовался Docker cache.
Условия, исходный JSON и ограничения: docs/PERFORMANCE.md.

Реализованные дополнительные возможности:
• What-if «выпуск резервного ТС»: сравнение следующих рейсов линии без/с резервом
  через 5–30 минут; допущения расчёта открыто показаны в карточке.
• Вероятность опоздания более 120 с с Platt-калибровкой; оценка вне фолдов
  одного дня: Brier 0,1065 с подсказкой и 0,1162 без неё.
• SHAP-объяснение прогноза: вклады групп признаков в секундах; вычисление
  по запросу и кэширование уменьшают нагрузку потокового цикла.
• Паспорт предупреждения: первое предупреждение, развитие прогноза,
  наблюдаемое GPS-прибытие, исход и фактическое упреждение по времени источника.
• Проблемные участки «где копится опоздание» по наблюдаемым прохождениям остановок.
• Приоритет первого/последнего рейса, рекомендации диспетчеру и подтверждение
  «принято в работу», сохраняемое в пределах эпизода ТС.
• Базовая GPS-привязка к плановой последовательности и фильтр подозрительных
  GNSS-фиксов; сложный дорожный map matching не заявляется.
• Переключение трёх демо-источников, просмотр истории NDTP без остановки приёма,
  автоматический сдвиг даты плана к дате потока, индикация устаревания данных.

Ограничения: геометрия маршрутов схематичная; what-if — сценарный расчёт,
а не транспортная модель города. Качество проверено на одном дне, независимый
новый день не оценивался. Итоговая v5 обучена на real train+test, поэтому MAE
replay по test помечен in-sample. Подробности функций: docs/FEATURES.md.
```
