```text
СВЕДЕНИЯ О ПРОИЗВОДИТЕЛЬНОСТИ

Latency (замеры p50 / p95):
• ML-модель v8, один прогноз: 6,2 / 7,1 мс в ONNX Runtime (CatBoost: 19,7 / 28,0 мс);
  пакет из 32 прогнозов — 11,1 / 13,8 мс.
• Сквозная цепочка в Docker (замер на предыдущей версии модели, код цепочки тот же):
  NDTP-поток от 30 бортовых терминалов с ускорением 60× — по частоте входящих пакетов
  в 60 раз выше реального потока этих ТС; 512 измерений:
  – запрос Backend → ML → Backend: 15,2 / 22,8 мс;
  – расчёт признаков: 42,3 / 65,0 мс;
  – от приёма телематического пакета до публикации прогноза: 172 / 317 мс
    (с учётом такта обработки Backend 0,5 с). Дашборд обновляется раз в секунду.

Надёжность:
• Приём NDTP: 29 532 кадра — 0 ошибок CRC, 0 битых и обрезанных кадров; TCP-поток
  разбирается с учётом дробления и склейки пакетов.
• Обрыв связи с источником: переподключение без перезапуска сервиса (в замере 8 обрывов,
  все соединения восстановлены); данные ТС помечаются устаревшими, показывается их возраст.
• Отказ ML-сервиса: Backend продолжает работать, показывает последний прогноз с его
  возрастом и статус «ML недоступен»; после восстановления прогнозы возобновляются
  без перезапуска.
• Без подсказки текущего отклонения работает отдельная автономная модель (fallback).
• Память ограничена окном состояния: за 30 минут потока Backend 137 → 139 МиБ,
  ML 84 → 85,5 МиБ.

Масштабируемость:
• ML-сервис отделён от Backend и не хранит состояние: можно запустить несколько
  экземпляров за балансировщиком. Прогнозы запрашиваются пакетами.
• Дообучение на новых данных — отдельной командой по зафиксированному рецепту,
  без изменения сервиса; модель подключается как версионированный комплект.

Ресурсы: инференс на CPU, GPU не требуется.

Точность: score платформы 0,95394 (метрика на основе MAE прогноза задержки за 10–15 минут).
Проверено в потоке: Backend, получая телеметрию validate потоком, выдал те же прогнозы,
что в отправленном CSV, — 139 из 139 числовых. Ещё 12 точек помечены «данные
устарели», потому что терминал в это время не передавал валидных координат.


РЕАЛИЗОВАННЫЕ ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ

1. Оптимизация инференса (ONNX): модель исполняется в ONNX Runtime, ускорение ×3,2
   на одиночном прогнозе без потери точности (расхождение < 0,0001 с). При старте
   сервис сверяет ONNX с CatBoost и при расхождении автоматически возвращается к CatBoost.
2. What-if анализ: оценка влияния выпуска резервного ТС на рейсы линии прямо
   в карточке ТС на дашборде.
3. Ансамбли моделей: 12 моделей CatBoost в двух ансамблях и классификатор
   «задержки не будет» на тех же признаках. Связка CatBoost + PyTorch (GRU по телеметрии)
   реализована и проверена, но в итоговую модель не вошла: точность не улучшилась.
4. Привязка координат к маршруту (базовая): сопоставление GPS с плановой
   последовательностью остановок и фильтр подменённых GNSS-координат.

Также реализовано:
• калиброванная вероятность опоздания более 2 минут (ROC-AUC 0,895: 1,0 — идеально,
  0,5 — случайно);
• объяснение каждого прогноза: вклад факторов в секундах (SHAP);
• паспорт предупреждения: когда система предупредила и что произошло фактически;
• проблемные участки маршрута, где копится опоздание;
• рекомендации диспетчеру и отметка «принято в работу»;
• мобильная версия (PWA);
• вход по ролям диспетчер/наблюдатель (включается переменной BACKEND_AUTH_USERS,
  по умолчанию выключен, чтобы стенд открывался без учётных записей);
• документация кода (Sphinx) и API (OpenAPI/Swagger).
```
